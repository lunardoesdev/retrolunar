## Compiles vs. useful — the honest framing

ptrace is a **runtime** mechanism. The question "does the NDK ship
`<sys/ptrace.h>`" has a clear answer, and it is yes — but headers existing only
gets the code to compile. Nothing here will ever *run* a strace built for
`aarch64-android35`, because this build host is x86-64 and this project never
installs an emulator. That is not a reason to refuse the recipe: the package
compiles, installs, and is useful to whoever later flashes it onto a device.

So the honest statement is: **compiles everywhere ptrace's headers exist;
useful only on `clang-native`, and on-device elsewhere.** This is exactly the
same shape as the `meson` and `lua` verdicts already in this tree — a target
binary that is inert until something runs it.

**libunwind is not needed.** The brief flagged it as optional and that is
right, but worth pinning down: it is gated behind `--with-libunwind`
(`configure --help`: *"use libunwind to implement stack tracing support"*),
`src/unwind-libunwind.c:12` is the only file that includes
`<libunwind-ptrace.h>`, and `USE_LIBUNWIND` (`src/config.h.in:1642`) stays
undefined when the flag is not given. `packages/libunwind` is therefore **not**
required. The 74 `unwind` hits in `configure` are the option plumbing and the
other unwinder backend, not a hard dependency.

**Risks / what a reviewer should check.**

1. **mingw is the real open question.** strace 7.2 is a Linux tracer;
   `configure.ac:439-503` probes a long list of Linux and glibc headers.
   Because every probe is an `AC_CHECK_HEADERS`/`AC_CHECK_TYPES` that records a
   0 rather than aborting, *configure* will almost certainly succeed. The risk
   is the subsequent compile. A reviewer should treat `x86_64-mingw` as
   UNCERTAIN and, if a build is attempted, expect missing Linux syscall
   headers rather than a configure failure. Nothing in this file invents a
   workaround for it.
2. **`--enable-mpers` is left at its default on purpose.** It defaults to
   `yes` (`configure.ac:763`) and its probes all degrade: the compile probe
   (`m4/mpers.m4:109-115`) is compile-only, the runtime probe at `:117-124`
   supplies a cross-compiling action that answers `no`, and the `mpers.sh`
   check at `:125-133` shells out only to `readelf`, a host tool. No
   `FATAL_ERROR` appears on the failure path. Turning it off would reduce
   fidelity for aarch64 tracees without fixing anything that is actually
   broken.
3. **aarch64 loses its AArch32 compat personality, silently and correctly.**
   `configure.ac:765-787` probes for a separate 32-bit compiler named
   `arm-linux-gnueabi{,hf}-gcc`, `arm7{,hl}-linux-gnueabi-gcc`, etc. The NDK
   ships no such binary — its wrappers are `armv7a-linux-androideabi*-clang`
   — so `CC_FOR_M32` is empty and `m4/mpers.m4:84` sets `CC=` to nothing for
   that personality, which the probes then report as unsupported. Worth
   knowing so a builder does not read the resulting messages as a defect.
4. **The timestamp guard touches `m4/*.m4` as well as the usual three.**
   strace carries real m4 inputs (`m4/mpers.m4` defines `st_MPERS`, used at
   `configure.ac:798-799`), so if `m4/` files land newer than `aclocal.m4` the
   autotools re-run this guard exists to suppress goes live. The order in the
   recipe is deliberate: m4 and the template first, then `aclocal.m4` and
   `configure`, then the `Makefile.in` sweep last so the generated makefiles
   end up newest.
5. **`--enable-install-tests` defaults to `no`** (`configure.ac:811`), so no
   test binaries are installed. No action needed; recorded so nobody adds the
   flag expecting it to matter.
6. **`AC_SEARCH_LIBS` calls for `dladdr`, `timer_create`, `clock_gettime`,
   `log10` and `mq_open`** (`configure.ac:666-708`). The Android systems
   already put `-lm` in `LDFLAGS`, which covers `log10`; the others resolve
   against Bionic's libc. Nothing extra is required here.
7. `topackage.md:374` lists strace unchecked; nothing else in the tree
   `require()`s it. Standalone.

**How to verify once built.**

- `bin/strace` exists and `[ -x bin/strace ]` is true.
- **`file bin/strace` / `$OBJDUMP -f bin/strace`** prints the expected machine
  — `ELF 64-bit LSB pie executable, ARM aarch64` on the Android systems,
  `PE32+` on mingw. This is the check that settles risk 1 without ever
  executing the binary.
- `llvm-nm --undefined-only bin/strace | grep -c ptrace` should be non-zero on
  a platform where ptrace is a real libc function; that is what proves the
  library actually bound the ptrace calls rather than compiling them out.
- `$READELF --version-info bin/strace` must show a minimum API level; on
  Android this should be the system's own API level, confirming the NDK
  wrapper's `__ANDROID_MIN_SDK_VERSION__` took effect.
- Do **not** run `bin/strace` from a target prefix, and do not install an
  emulator to do so. On `clang-native` only, `bin/strace --version` and a
  trivial `strace -o /dev/null true` are acceptable — that is the one system
  where the artifact is genuinely runnable.
