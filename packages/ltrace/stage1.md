# ltrace build forecast

- Recipe: `generic.lua`, source `source.lua`
- Version pinned: 0.7.3
- **Correction to the backlog's assumption:** the brief described ltrace as a
  possibly-archived, 0.4-era project. That is wrong. 0.7.3 exists, is
  packaged by Debian as `0.7.3-6.1`/`-6.4`, and is what this recipe pins. But
  the tarball's own mtimes are `Sep 17 2013` and the configure banner records
  `Autoconf 2.68 for ltrace 0.7.3`, so 0.7.3 is itself from 2013 — roughly
  thirteen years without a release. "Not archived, but very quiet" is the
  accurate description.
- Build system: **autotools, with a generated `configure` that ships.**
  443718 bytes, banner `# Generated by GNU Autoconf 2.68 for ltrace 0.7.3.`
  The banner is the evidence; size alone proves nothing against a truncated
  download.
- **Config template: `config.h.in`, at the top level**, from `configure.ac:27`
  `AC_CONFIG_HEADERS([config.h])`. Verified present. Not `src/config.h.in`,
  not `config-h.in`, not `config.hin`.
- Requires: `elfutils` (libelf, a hard dependency) and `ltrace@source`.

## The decisive reason

`configure.ac:34-38`:

```m4
case "${host_os}" in
    linux-gnu*) HOST_OS="linux-gnu" ;;
    linux-uclibc*) HOST_OS="linux-gnu" ;;
    *)		AC_MSG_ERROR([unkown host-os ${host_os}]) ;;
esac
```

`host_os` is derived from `--host` by autoconf's canonicalisation
(`AC_CANONICAL_HOST`, `configure.ac:32`). Our systems export:

| system | `HOST_TRIPLET` | `host_os` | result |
|---|---|---|---|
| `aarch64-android*` | `aarch64-linux-android` | `android` | **`AC_MSG_ERROR`** |
| `x86_64-mingw` | `x86_64-w64-mingw32` | `mingw32` | **`AC_MSG_ERROR`** |
| `clang-native` | `x86_64-pc-linux-gnu` | `linux-gnu` | accepted |

So configure **fails immediately**, before compiling anything, on every system
in this tree except `clang-native`. The error text is `unkown host-os android`
(spelled that way upstream).

**This is not a ptrace problem and not a header problem.** The brief asked
whether ptrace would compile. It would: `breakpoints.c:33` includes
`<sys/ptrace.h>`, and the NDK 28.2 sysroot does ship `sys/ptrace.h` (2421
bytes) and `sys/user.h` (5574 bytes). ltrace never gets far enough to find
out — the host-OS whitelist rejects the triplet first, and it does so on a
value this project must not change, because `HOST_TRIPLET` is a machine
identity fact that belongs in the system files. Overriding `--host` would
misrepresent the target, and editing `configure.ac` would be patching
upstream. Neither is done.

Note also that the only `sysdeps/` directory ltrace ships is `linux-gnu`
(`configure.ac:311-321` generates `sysdeps/linux-gnu/*/Makefile` for alpha,
arm, cris, ia64, m68k, mips, ppc, s390, sparc, x86). There is no `sysdeps`
entry for Android at all, so even past the whitelist there would be no
architecture-specific register access code to compile.

**API level notes.** Not reached — configure aborts first. For the record, on
`clang-native` nothing in the API-gate list applies (ltrace does not use
`posix_spawn`, `process_vm_readv`, `POSIX_MADV_*`, `mblen`, `getpass`,
`O_BINARY`, `nl_langinfo` or `mktime_z`). `armv7a-android*` and
`i686-android*` match `aarch64-android*`.

**Risks / what a reviewer should check.**

1. **`--disable-libunwind` is load-bearing and counter-intuitive.** The option
   defaults to `maybe` (`configure.ac:133`), not `no`, and `maybe` means "turn
   it on if either header is visible" (`configure.ac:143-145` tests
   `have_libunwind_h = yes` **-o** `have_libunwind_ptrace_h = yes`).
   `packages/libunwind` installs `libunwind.h`, so the default would flip this
   to **yes** — and then `configure.ac:176-178` runs
   `AC_CHECK_LIB([unwind-ptrace], [_UPT_create], ...,
   [AC_MSG_ERROR([Couldn't find or use libunwind-ptrace.])])`.
   Our libunwind is built without ptrace support, so that library is absent and
   **configure aborts**. Leaving the flag off would therefore be a latent
   configure failure on `clang-native` that only appears once libunwind is in
   the prefix. This is the single most valuable thing to get right here.
2. **libelf is mandatory.** `configure.ac:64` aborts with
   `*** libelf is a required dependency` when libelf is absent, and
   `configure.ac:83-87` aborts if `libelf.h`/`gelf.h` are missing.
   `require("elfutils")` is therefore not optional and not cosmetic.
   `--with-libelf=PATH` exists for a non-standard location.
3. **`configure.ac:94-110` probes for a C++ demangler** —
   `cplus_demangle` in `libiberty`, then `__cxa_demangle` in `libsupc++`,
   then in `libstdc++`. These are plain `AC_CHECK_LIB` with fallback actions,
   so a miss degrades gracefully rather than aborting. Worth confirming which
   one was found, since it changes what `ltrace` can print.
4. **Source URL was not verifiable from the build environment.**
   `gitlab.com` is behind a Cloudflare challenge here (every request returns
   `Just a moment...`), so the canonical gitlab archive path could not be
   confirmed. The recipe lists that path first and falls back, on the same
   line, to the Debian pool orig tarball, which is the upstream tarball
   verbatim and is what was actually downloaded and read. The fallback is
   `.tar.bz2`, hence `tar -xjf`.
5. `topackage.md:375` lists ltrace unchecked; nothing else in the tree
   `require()`s it. Standalone.

**How to verify once built (clang-native only).**

- On any Android or mingw system the build is expected to **fail at
  configure**, and the signature is the literal string `unkown host-os`. If a
  log ever shows something else failing first, that is a different defect.
- On `clang-native`: `bin/ltrace` exists and `[ -x bin/ltrace ]` is true.
- `$READELF -d bin/ltrace | grep NEEDED` should list `libelf.so`, which is the
  check that the mandatory dependency actually bound.
- Only on `clang-native` may you run `bin/ltrace --version`, or something like
  `ltrace -o /dev/null /bin/true`. Do not attempt either from a target prefix.
