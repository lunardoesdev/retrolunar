# oneDPL build forecast

- Recipe: `generic.lua`, source `source.lua`
- Version pinned: 2022.14.0 (tag `oneDPL-release-2022.14.0`)
- Build system: CMake (header-only)
- Installs: the whole `include/` tree (`CMakeLists.txt:367`), `dpl.pc`, a
  generated `oneDPLConfig.cmake` + version file under `lib/cmake/oneDPL/`
  (`:364-369`, generated by `cmake/scripts/generate_config.cmake`), the
  `licensing/` directory and two Windows-only helper `.cmake` files.
- Requires: `dpl@source` only. No dependencies **given `ONEDPL_BACKEND=serial`**
  (see below).
- Upstream identity: the project moved to `github.com/uxlfoundation/oneDPL`;
  the tree's own README links there. 2022.14.0 is the newest release tag on
  either repository (checked via the releases atom feed and the tags page,
  since the REST API rate-limited).

**The headline question — is oneDPL usable standalone? Yes, but only with an
explicit backend.** The brief expected it not to be. What is actually true:

- oneDPL is header-only (`add_library(oneDPL INTERFACE)`,
  `CMakeLists.txt:151`), so nothing is compiled and the install is a file copy
  identical on every system.
- **Left alone it is NOT standalone.** `CMakeLists.txt:138-146` defaults
  `ONEDPL_BACKEND` to `"tbb"` whenever SYCL is absent — and SYCL is always
  absent here, since `-fsycl` does not exist on clang/gcc. The `tbb` branch at
  `:210-214` then runs `find_package(TBB 2021 REQUIRED tbb OPTIONAL_COMPONENTS
  tbbmalloc)` and links `TBB::tbb`. Configuring without oneTBB installed
  **fails hard**.
- `-DONEDPL_BACKEND=serial` takes the branch at `:283-289`, which defines
  `ONEDPL_USE_TBB_BACKEND=0`, `ONEDPL_USE_DPCPP_BACKEND=0` and
  `ONEDPL_USE_OPENMP_BACKEND=0` and requires no external library at all. That
  is what this recipe passes, and it is a real upstream option, not a hack.
- **Probe:** `#include <oneapi/dpl/execution>` and `<oneapi/dpl/algorithm>` with
  a real `oneapi::dpl::sort(oneapi::dpl::execution::seq, ...)`, all three
  backend macros forced to 0, `-fsyntax-only`:
  **OK at API 21, 24 and 35 at `-std=c++17` and `-std=c++20`; OK on mingw
  g++ 16.2.0 at both; OK on native clang++ at both.**
- C++17 is the floor: `target_compile_features(oneDPL INTERFACE cxx_std_17)`
  (`:152`). That is satisfied by every toolchain here without a flag — the NDK
  wrapper defaults to `__cplusplus` 201703L (probed with `-dM`), mingw g++ 16.2
  defaults to 202002L, native clang++ to 201703L.

**Test tree — entered, but builds nothing.** `CMakeLists.txt:356-359` adds
`test/` whenever oneDPL is top-level, which it always is here. That looks
alarming, but every executable in it is `EXCLUDE_FROM_ALL`:
`test/CMakeLists.txt:92` and `test/kt/CMakeLists.txt:26`. A grep for
`add_executable` across the whole tree finds non-`EXCLUDE_FROM_ALL` calls only
under `examples/`, which is **never added** — the sole `add_subdirectory`
outside `test/` does not exist in this project. So `cmake --build` compiles
nothing from tests. Note there is **no** `BUILD_TESTING`-style option to turn
the directory off; `EXCLUDE_FROM_ALL` is the mechanism upstream uses.

**Risks / what a reviewer should check.**

1. **`ONEDPL_BACKEND=serial` is a real product decision, not just a build
   convenience.** A consumer that wants oneDPL's actual parallel execution gets
   `oneapi::dpl::execution::par_unseq` running sequentially. The alternative —
   defaulting to `tbb` — makes oneDPL depend on `packages/tbb`, which this
   recipe does *not* pull in. If parallel execution is wanted later, the
   change is `-DONEDPL_BACKEND=tbb` plus `require("tbb")`, and it works because
   the tbb recipe builds.
2. **`TBB_USE_GLIBCXX_VERSION` is set from the HOST g++.** `CMakeLists.txt:217-227`
   runs `find_program(FIND_GXX_EXE g++)` and, for a Clang C++ compiler on UNIX,
   defines `TBB_USE_GLIBCXX_VERSION=<host g++ version>` (here 16.2 → 1602001).
   `find_program` searches the host, and `CMAKE_FIND_ROOT_PATH_MODE_PROGRAM` is
   `NEVER` in our toolchain files, so this genuinely picks up the build machine's
   g++. It is an INTERFACE compile definition only, recorded in the installed
   config — it does not affect this build, and with the serial backend no TBB
   header reads it. Worth knowing before anyone wonders.
3. **`ONEDPL_ENABLE_SIMD` stays ON** (`:29`). It adds `-fopenmp-simd`-style
   flags to the INTERFACE target, but only after `check_cxx_compiler_flag`
   accepts one (`:177-185`), so it is a no-op on compilers without it.
4. **`cmake_minimum_required` is 3.20 on Windows / 3.11 elsewhere**
   (`:15-21`). Both clear the 3.5 floor every system already carries, so the
   recipe hardcodes no `CMAKE_POLICY_VERSION_MINIMUM` and relies on
   `$CMAKE_FLAGS`, per AGENTS.md.
5. **Install uses `install(SCRIPT ...)`** (`:366`), so the generated
   `oneDPLConfig.cmake` and `dpl.pc` land under `lib/cmake/oneDPL/`. The loader
   rewrites `$OUT`→`$PREFIX` in staged `.pc` files, so `dpl.pc`'s
   `prefix=${pcfiledir}/../../` needs no rewriting.

**How to verify once built.**

- `include/oneapi/dpl/execution` and `include/oneapi/dpl/algorithm` exist.
- `include/oneapi/dpl/internal/version_impl.h` exists and
  `grep -q 'ONEDPL_VERSION_MAJOR 2022'` it.
- `lib/cmake/oneDPL/oneDPLConfig.cmake` exists.
- `pkg-config --modversion oneDPL` reports 2022.14.0 — **note the module name
  is `oneDPL`, not `dpl`**, while the *directory* here is `dpl`.
- **No library file:** `find $OUT -name '*.a' -o -name '*.so'` must return
  nothing — the check that proves the serial-backend install is header-only.
- **No test binaries:** `find $OUT -name '*_test' -o -name 'test_*'` must
  return nothing (risk 3).
- `grep -q 'ONEDPL_USE_TBB_BACKEND=0' lib/cmake/oneDPL/oneDPLConfig.cmake`
  confirms the backend actually recorded is serial (risk 1).
