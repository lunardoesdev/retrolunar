**API level notes.** None apply. Nothing here opens a file, spawns a process
or touches `stderr` at build time; `O_BINARY`, `posix_spawn` and
`POSIX_MADV_*` are all irrelevant to a compile-only build of a formatter.
`armv7a-android*` and `i686-android*` match `aarch64-android*`.

**Risks / what a reviewer should check.**

1. **The `find_package(Python3 REQUIRED)` at `CMakeLists.txt:28` is a HOST
   tool and is correct as one.** Under cmake 3.12+ the file takes the
   `else()` arm at `:27` and calls `find_package(Python3 REQUIRED)`; only for
   cmake older than 3.12 does it fall back to `PythonInterp` with a
   `FATAL_ERROR` if absent (`:22-26`). The host running the build has python3,
   and our cross systems deliberately do not overwrite `PATH` with the target
   toolchain, so this resolves to the build machine. **It must not be
   `require("python")`** — that would pull a *target* python into the search
   path and still not satisfy a host `find_package`.
2. **Host codegen runs python scripts over upstream sources** —
   `py_gen` (`CMakeLists.txt:189-211`) invokes
   `scripts/make_options.py` and `scripts/make_punctuator_table.py`, and
   `add_custom_command` at `:169-177` runs `cmake/GenerateTokenNames.cmake`.
   All host-side, none of it executes a target binary. Correct on cross.
3. **There is deliberately NO `-DNoGitVersionString` here**, and that is a
   considered decision, not an omission. The option defaults OFF
   (`CMakeLists.txt:141`), so by default a custom target runs
   `cmake/GenerateVersionHeader.cmake`, which shells out to
   `scripts/make_version.py` to read a git SHA. Read
   `cmake/GenerateVersionHeader.cmake:17-33`: upstream explicitly expects
   this to fail for a tarball ("It's normal for make_version.py to fail when
   building from a tarball"), reports it as a `STATUS` message, and falls back
   to the static `UNCRUSTIFY_VERSION` set at `CMakeLists.txt:139`. So the
   default *is* the path designed for our case. A reviewer who adds
   `-DNoGitVersionString` is changing behaviour to avoid a message upstream
   already handles; it would also drop the `generate_version_header` dummy
   target at `:144`. Worth confirming the built binary reports `0.83.0`.
4. **`-DBUILD_TESTING=OFF` is deliberate.** `include(CTest)` at
   `CMakeLists.txt:20` defines `BUILD_TESTING` ON by default, and `:565-567`
   then does `enable_testing()` + `add_subdirectory(tests)`. Those tests are
   only ever executed by `ctest`, which a cross build never runs, so they
   would be compiled for nothing. Note this is the CTest module's option
   name, not a project-specific one — confirmed at `:565`.
5. **The man page is not generated by running the tool.**
   `CMakeLists.txt:551-553` does a plain `configure_file(man/uncrustify.1.in
   uncrustify.1 @ONLY)`. This matters: the tree's flex recipe documents a
   closely related failure where a help2man rule fired and `make install` died
   on `cannot stat`. Here there is no help2man and no regeneration rule, so
   no equivalent trap.
6. `topackage.md:350` lists uncrustify unchecked; nothing else in the tree
   `require()`s it. Standalone, no recorded build.

**How to verify once built.**

- `bin/uncrustify` exists and `[ -x bin/uncrustify ]` is true.
- `bin/uncrustify --version` must not be run on a cross system — read the
  version out of the binary instead (e.g. `strings`), and check it reports
  `0.83.0`, which proves the tarball fallback at
  `GenerateVersionHeader.cmake:29-33` took.
- `share/man/man1/uncrustify.1` exists — this is the check that distinguishes
  the GNUInstallDirs arm (`:635-637`) from the MSVC arm (`:619-621`), and it
  is the single best proof that the install layout was the one we expect.
- `$OBJDUMP -f bin/uncrustify` prints the expected machine (ELF 64-bit
  aarch64 / PE for mingw).
- On `x86_64-mingw` specifically, expect the binary to be named `AStyle`,
  not `astyle` (`CMakeLists.txt:191-195`).
