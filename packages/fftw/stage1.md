# fftw build forecast

- Recipe: `generic.lua`, source `source.lua`
- Version pinned: **3.3.11** (the newest in `www.fftw.org/pub/fftw/`, whose
  listing ends `...3.3.10.tar.gz`, `fftw-3.3.11.tar.gz`; 3.3.10 is not
  current)
- Build system: **autotools**, and the release tarball ships a generated
  `configure` (`configure` is 834151 bytes and contains
  `Generated by GNU Autoconf 2.69`). No `autoreconf` is needed or wanted.
- Config template: **`config.h.in`** — `configure.ac:33` is
  `AM_CONFIG_HEADER(config.h)`, so the template is top-level `config.h.in`
  (12425 bytes). Note there is a second, unrelated `cmake.config.h.in`
  (11603 bytes) used only by `CMakeLists.txt`; the autotools guard must name
  `config.h.in` and not that one.
- Installs: static `libfftw3.a`, the `fftw3.h` family, `fftw3.pc`
  (`Makefile.am:166-169`) and an `FFTW3Config.cmake` package config
  (`Makefile.am:171-181`). Also `bin/fftw3-wisdom` and its man page
  (`tools/Makefile.am:3`), which are target programs and are never run here.
- Requires: `fftw@source` only. No dependencies.

## The cross-compilation question, answered from the tree

The brief expected a runtime timing probe in configure and a switch to turn
it off. **That is not what fftw 3.3.11 does, and no such switch is needed.**
Three findings, each from a verified non-empty file:

1. **There is no codelet-select timing machinery in the tree at all.**
   Searching the whole unpacked tree for `codelet select`, `codelet_select`
   and `CODLET_LIST` returns **zero files**. Older FFTW (3.1/3.2 era) chose
   among pre-generated codelets by compiling and *running* a selector during
   the build; that machinery is not in 3.3.11.
2. **Every SIMD family is opt-in at configure time and defaults off.**
   `configure.ac:119` `--enable-sse2`, `:138` `--enable-avx2`, `:192`
   `--enable-neon` (and the rest) all end `have_*=$enableval, have_*=no`.
   Not passing any of them is the "disable the cpuinfo/timing path" answer:
   the recipe builds plain scalar codelets, and no build decision depends on
   which CPU is doing the building.
3. **The per-CPU detection that does exist is a library *runtime* check, not a
   build-time one.** `simd-support/x86-cpuid.h` and `simd-support/sse2.c`
   compile a CPUID test *into the library*; they run on the target at
   execution time and never during the build.

Nothing in the build executes a compiled program. `configure` links autoconf
probes, which is what `$AUTOCONF_CONFIGURE_FLAGS --host=...` exists for, and
`make` compiles two programs without running either: `tests/bench`
(`tests/Makefile.am:2`, `noinst_PROGRAMS`, not installed) and
`bin/fftw3-wisdom` (`tools/Makefile.am:3`, installed but never executed here).
`mpi/` is inside `if MPI` (`mpi/Makefile.am:6`) and `--enable-mpi` defaults
off (`configure.ac:322`), so nothing there is built. `genfft` is inside
`if MAINTAINER_MODE` (`Makefile.am:8`) and is off by default.

**API level notes.** None of the API-21 walls (`stderr` as a real symbol,
`POSIX_MADV_*`, `process_vm_readv`, `posix_spawn`, `mblen`, `getpass`,
`O_BINARY`) is reachable from fftw, and neither are the higher gates
(`nl_langinfo` 26, `iconv.h` 28, `mktime_z` 35). The `AC_CHECK_FUNCS` list at
`configure.ac:613` contains only API 21 names; every one that could be absent
is guarded with a fallback. `armv7a-android*` and `i686-android*` match
`aarch64-android*`.

**Risks / what a reviewer should check.**

1. **`--disable-fortran` is mandatory, not cosmetic.** `configure.ac:679`
   defaults the Fortran-callable wrappers **on**, and the branch runs
   `AC_PROG_F77` (`configure.ac:682`). No system in `packages/` exports `$FC`
   or `$F77`, and there is no gfortran or flang on this build host, so leaving
   it on makes configure reach for a Fortran compiler that is not there.
   (`AC_PROG_F77` failing is survivable — `:683-685` warns and falls back to
   the default wrappers — but the wrappers themselves still need a compiler to
   build, so the switch is what actually saves the build.)
2. **`--disable-doc` is mandatory in this prefix.** `doc/Makefile.am:3` is
   `info_TEXINFOS = fftw3.texi`, which automake builds through `makeinfo`.
   `topackage.md:81` records Texinfo 7.3 as blocked. `--disable-doc` sets
   `build_doc=no` (`configure.ac:54`), which blanks `DOCDIR` at
   `Makefile.am:36-40` and drops `doc/` from `SUBDIRS` (`Makefile.am:42-43`).
3. **The timestamp guard names the right template.** `config.h.in` at the top
   level is the autotools template (`configure.ac:33`); `cmake.config.h.in` is
   the cmake one (`CMakeLists.txt:304`). Touching the wrong one is the inert
   guard AGENTS.md warns about — `touch` on a missing file in an existing
   directory succeeds and creates it.
4. **Threads are deliberately left off**, and that is a real decision, not an
   omission. `--enable-threads` (`configure.ac:731`) drives the `ACX_PTHREAD`
   probe at `configure.ac:759-763`, which on a cross build fails to find a
   separate pthreads library and can leave a `-lpthread` no Android sysroot
   will satisfy — the same defect `topackage.md:126-133` records for ISA-L.
   Single-threaded FFTW is the correct default for a library prefix, and a
   consumer wanting threads can add it later.
5. **`--enable-static --disable-shared` with `--with-pic`** matches the
   repo-wide static-only policy. `--with-pic` defaults to "use PIC for both",
   so it is explicit rather than a change of behaviour.
6. **The SIMD answer is a policy choice worth naming.** A scalar libfftw3.a
   is correct everywhere and portable, which is what a shared prefix wants.
   A consumer wanting NEON performance adds `-DFFTW_ENABLE_NEON` or rebuilds
   with `--enable-neon`. Recording that explicitly stops the next person
   reading "no `--enable-neon`" as an oversight.

**How to verify once built.**

- `lib/libfftw3.a` exists.
- `include/fftw3.h` exists.
- `pkg-config --modversion fftw3` reports 3.3.11.
- `$OBJDUMP -f lib/libfftw3.a` prints `elf64-littleaarch64` on Android.
- `llvm-nm --defined-only lib/libfftw3.a | grep -cw fftw_plan` — expected
  **non-zero**; `fftw_plan` is the one symbol every consumer needs and its
  absence would mean a truncated or wrong archive.
- `grep -c 'HAVE_NEON\|HAVE_AVX2\|HAVE_SSE2' $WORK/config.h` should be **0
  nonzero defines** — that is the check that the scalar build actually
  happened. State the expected value (zero) so it can be compared rather
  than inferred.
- `ls $OUT/bin/` — expected to contain `fftw3-wisdom` only, and it must be
  `ELF 64-bit LSB pie executable, ARM aarch64` (a target binary that is
  installed and never run).
