# distcc build forecast

- Recipe: `generic.lua`, source `source.lua` (GitHub release asset)
- Version pinned: **3.4** (tag `v3.4`, "3.4 Lax lexer" — the current
  `releases/latest`)
- Build system: **autoconf only, no automake.** `configure.ac:11` states
  "As of 0.6cvs, distcc no longer uses automake, only autoconf", and the
  tree bears that out: there is no `Makefile.am` and exactly one
  `Makefile.in` at the top level.
- A **generated `configure` does ship**: 249842 bytes, and
  `configure:1` reads `# Generated by GNU Autoconf 2.69 for distcc 3.4.`
  (verified against the downloaded archive, not assumed from its size).
- **Config template: `src/config.h.in`**, named by
  `AC_CONFIG_HEADERS(src/config.h)` at `configure.ac:15`. There is no
  top-level `config.h.in`; `ls config.h.in` fails.
- **Not a sub-configured project, despite appearances.**
  `AC_CONFIG_FILES([Makefile] popt/.stamp-conf lzo/.stamp-conf)` at
  `configure.ac:541` makes it look like one, but `popt/` and `lzo/` are
  vendored *source* directories: neither has a `configure.ac`, a
  `configure`, an `aclocal.m4` or a `Makefile.in`, and both hold only
  `.stamp-conf.in` plus plain C sources. distcc's own `Makefile.in:394-402`
  compiles them. So one template and one `Makefile.in`, both at the top
  level — as the guard in `generic.lua` assumes.
- Installs: `bin/distcc`, `bin/distccd`, `bin/distccmon-text`,
  `bin/lsdistcc`, `sbin/update-distcc-symlinks` (`Makefile.in:417-425`) and
  six man pages (`Makefile.in:385-386`). No library, no headers, no `.pc`.
- Requires: `distcc@source` only. No `require()` on any other package:
  popt and lzo are vendored, and `--with-included-popt` makes that explicit.

## Native tool, not a target library

`distcc` is a compiler wrapper and `distccd` is a network compile-server
daemon. `distcc` exists to be invoked as `distcc gcc ...`, so it must run on
the machine holding the compiler; `distccd` serves preprocessed jobs over
TCP to such a machine. Neither has a consumer inside an Android or mingw
target prefix — there is no target compiler there to wrap and no build to
serve. **The only system that actually consumes this package is
`clang-native`**, and a consumer should spell it `require("distcc@native")`.

`@native` resolves to `clang-native` and then falls back to this
`generic.lua`, so no `clang-native.lua` is needed: the file would be a
byte-identical copy of `generic.lua`, which is precisely what
`packages/bison/android.lua` was for and was deleted. The same is true for
`re2c` and `ragel` in this same batch.

## API level notes

**The API level is not the variable for this package.** distcc 3.4 reaches
for nothing gated above API 21 — the one symbol in the recorded wall list it
does use, `O_BINARY`, is defined away to `0` by its own header. Raising the
level changes nothing here. This is unlike `ninja`, whose blocker *is* an
API-level wall.

The one real cross-compilation cost is the `AC_TRY_RUN` pair above: autoconf
substitutes `cross` for both, so two features silently switch off. Worth
knowing if a builder sees distcc behave differently in a target prefix.

## Risks / what a reviewer should check

1. **The config-template name in the guard is the load-bearing detail.**
   `src/config.h.in` is the only `*.h.in` in the tree, and it is easy to
   write `config.h.in` from habit. `touch` on a missing file in an existing
   directory succeeds and creates it, so a wrong name raises nothing under
   `set -eu` and the autoheader re-run the guard exists to suppress stays
   live. Confirmed present, 8374 bytes, by `ls -l src/config.h.in`.
2. **`--with-included-popt` is a deliberate choice, not a workaround.** The
   auto-detect at `configure.ac:320-328` would land on the bundled copy
   anyway; passing it removes a link probe. No `popt` package is required
   and none exists in this tree.
3. **`--disable-pump-mode` drops a feature.** Pump mode is the include
   server. Nothing in this prefix consumes it, and its man page still
   installs, but a reviewer who wants `distcc` to serve include requests
   should know it is off and that the switch is one token away.
4. **The man pages are shipped, not generated.** `man1_MEN`
   (`Makefile.in:385`) is installed by `install-man` (`Makefile.in:1103`),
   which only gzips them — no `help2man`, no `fig2dev`, so there is no
   run-a-built-binary hazard of the kind `packages/flex` has to work around.
5. **No host programs are built or run.** `check_PROGRAMS`
   (`Makefile.in:427-440`) and `check_include_server_PY` (`:441-450`) are
   reachable only from `make check`, which this recipe never invokes. That
   is what keeps the no-execution rule satisfied on a cross build.

## How to verify once built

- `bin/distcc`, `bin/distccd`, `bin/distccmon-text`, `bin/lsdistcc`,
  `sbin/update-distcc-symlinks`
- six files under `share/man/man1/`
- **no `lib/` artifacts and no `.pc`** — the absence is the check that
  `--with-included-popt` took and that no shared `libpopt` leaked in
- `file bin/distcc` → host x86_64 ELF on `clang-native`
- `bin/distcc --version` is safe to run **on `clang-native` only**; it is a
  host binary there. Never run it from a target prefix.
