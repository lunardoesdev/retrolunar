# stage1 — Universal-Ctags 6.2.1 (build forecast)

## Which tarball, and why it matters

The **release asset** `universal-ctags-6.2.1.tar.gz` is used, not the
`v6.2.1` tag snapshot. This is not cosmetic — they are different trees:

- Tag snapshot (`archive/refs/tags/v6.2.1.tar.gz`, 3289711 bytes, 9146
  entries): **no `configure`, no `aclocal.m4`, no `Makefile.in`, no
  `config.h.in`**. Only `configure.ac` and `autogen.sh`, which runs
  `autoreconf -vfi` (autogen.sh:38). Building it would need host autotools.
- Release asset (`releases/download/v6.2.1/universal-ctags-6.2.1.tar.gz`,
  3122094 bytes, 8835 entries): ships the generated build system.

Both downloads were size-checked against the server `content-length` and
listed with `tar tf` before extraction. The release asset is used, so no
autoreconf is required here.

## The one flag that needs a reason

`--disable-external-sort` is load-bearing, not cosmetic.
`configure.ac:499-517` runs the **build host's `sort` binary** as a
configure-time probe:

```
touch ${tmpdir}/sort.test
sort -u -f -o ${tmpdir}/sort.test ${tmpdir}/sort.test 1>/dev/null 2>&1
```

If that succeeds, `EXTERNAL_SORT` is defined and ctags shells out to
`sort` at run time. Left alone, the configured feature set would depend on
whichever `sort` the build host happens to carry — and on this machine
`sort` has already been observed failing with `Disk quota exceeded`
(spilling a temp file into a full `$TMPDIR`), which is exactly the kind of
host-state dependence that should not decide a cross build's feature set.
`--disable-external-sort` selects the internal algorithm and makes the
build self-contained.

This is a host *tool* invocation at configure time, not a target binary, so
it is not an emulation problem — but removing the dependence is still the
right call.

`--disable-xml/json/yaml/seccomp/pcre2`: each is a `pkg-config` probe
(`configure.ac:706-780` for libxml, with the matching blocks for the
others). Every system pins `PKG_CONFIG_LIBDIR` to `$PREFIX` and the NDK
sysroot and empties `PKG_CONFIG_PATH` (e.g.
`packages/aarch64-android24/generic.lua:89-95`), so these already
auto-disable and cost nothing. They are passed explicitly so the choice is a
decision in the recipe rather than an accident of what happens to be in the
prefix. None of them adds a dependency.

## Caveat worth flagging to the builder

I am confident on the build system and the option list because both were
read in the real tree. The residual risk is in **the parsers**, which are
thousands of generated `.c` files (`parsers/`) that I counted but did not
audit for Android-specific libc calls. That is why no row is UNCERTAIN —
the build system is the part that historically breaks under cross
compilation, and it is sound here — but a builder hitting a parser failure
should read it as new information rather than as contradicting this row.

## Notes for the reviewer

- Timestamp guard touches `aclocal.m4 configure config.h.in
  man/GNUmakefile.in`, then sweeps every `Makefile.in`. The
  `man/GNUmakefile.in` entry is the one a `find -name Makefile.in` sweep
  silently misses.
- Build never fans out: `make -j1`.
