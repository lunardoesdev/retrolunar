## 2. Is it doing what the package needs?

**The generated `configure` is real and the version matches.** Measured:

```
-rwxr-xr-x 649280  configure
line 3: # Generated by GNU Autoconf 2.72 for universal-ctags 6.2.1.
```

So no `autoreconf` — the recipe is right to avoid the cmph/minizip problem
entirely.

**The guard is correct, and the `man/GNUmakefile.in` catch is a real catch.**
This is the most interesting thing in the recipe:

- `configure.ac:33` is `AC_CONFIG_HEADERS([config.h])` and `config.h.in`
  exists (43,058 bytes). Correct template name.
- `configure.ac:992` is `AC_CONFIG_FILES([Makefile gnulib/Makefile
  man/GNUmakefile])`. `man/GNUmakefile.in` exists (51,571 bytes) and is
  **not** caught by `find . -name 'Makefile.in'` — the name has a `GNU`
  infix. Without naming it, the `man/` sub-configure's maintainer-mode
  rebuild rule stays live, which is the same silent failure as a sub-configured
  project. This is precisely the class of thing AGENTS.md's guard section
  warns about, found correctly.
- Guard position is right: after `./configure`, touching `aclocal.m4 configure
  config.h.in man/GNUmakefile.in`, then sweeping `Makefile.in`.

`grep -c AC_CONFIG_SUBDIRS configure.ac` is not exercised because the recipe
already handles the sub-`Makefile`s (`gnulib/Makefile` *is* matched by the
`find`, and `man/GNUmakefile` is named explicitly). Complete.

**All six `--disable-*` flags are real.** This is where I nearly recorded a
false defect: `grep -c "AC_ARG_ENABLE(xml,"` returns 0, because the file
spells it `AC_ARG_ENABLE([xml],` with brackets. Checking the generated
`configure --help` instead — the authoritative test, since it is the script
that must accept the flag — gives:

```
--disable-xml          in --help
--disable-yaml         in --help
--disable-json         in --help
--disable-seccomp      in --help
--disable-pcre2        in --help
--disable-external-sort in --help
```

All six recognised. Confirmed at source: `configure.ac:706-707`
(`AC_ARG_ENABLE([xml], … --disable-xml)`), `:808-810` (`json`), `:829-831`
(`seccomp`), `:194-195` (`external-sort`), and the matching yaml/pcre2 blocks.
**No nonexistent flag.** (Recorded because the bracket-vs-paren spelling is a
trap that would have produced a wrong REJECT.)

**`--disable-external-sort` is the one load-bearing switch, and the reason is
right.** `configure.ac:479-500` runs the **build host's** `sort` binary as a
configure-time probe:

```
AC_CHECK_PROG(sort_found, sort, yes, no)
if test "$sort_found" = yes ; then
    touch ${tmpdir}/sort.test
    sort -u -f -o ${tmpdir}/sort.test ${tmpdir}/sort.test 1>/dev/null 2>&1
    if test $? -ne 0 ; then … else AC_DEFINE(EXTERNAL_SORT) …
```

Two problems, both real: (a) it *runs a host program* whose availability
depends on the build machine, and (b) whether `EXTERNAL_SORT` gets defined
becomes a function of that host's `sort`, so the configured feature set is not
reproducible across machines. Turning it off selects the internal algorithm
(`configure.ac:499-517`, "using internal sort algorithm as fallback") and
makes the build self-contained. That is the same "configure-time behaviour
should not depend on the build host" concern that `--without-python` addresses
in libxslt, and it is handled the same way — correctly.

The four library flags (`--disable-xml/json/yaml/seccomp/pcre2`) are each a
`pkg-config` probe, and every system pins `PKG_CONFIG_LIBDIR` to `$PREFIX` (plus
the NDK sysroot) with `PKG_CONFIG_PATH=""`, so they would auto-disable anyway.
Passing them makes the choice a decision in the recipe rather than an accident
of the prefix. Correct, and cheap.

**No host program that matters, and no target binary is run.** The only
`AC_PROG`-style execution is `sort`, now disabled. universal-ctags is a
program, not a library, so it is compiled and installed but never executed
during the build.

## API gates

The one worth naming is `mblen`, and this package does probe it —
`configure.ac:990` is `AC_CHECK_FUNCS(mblen)`. Per the known-walls list,
API 21 lacks `mblen`. That is a `AC_CHECK_FUNCS` link probe, so on Android 21
it simply fails and `HAVE_MBLEN` goes undefined — a feature flag, not a build
break, since `AC_CHECK_FUNCS` never aborts. No `nl_langinfo`, `mktime_z`,
`process_vm_readv`, `O_BINARY` or `posix_spawn` anywhere. So the API level does
not gate this build, and the WILL BUILD rows at 21 are sound.

## Artifacts — what actually installs

- `bin/ctags` — and `bin/universal-ctags` as a relative symlink
- `share/man/man1/ctags-universal.1`
- `share/man/man3/*.3` — the ~100+ parser man pages
- `include/ctags.h`, `lib/libctags.a` — the optional **library** build
  (universal-ctags builds `libctags` when `--enable-xmldoc`/shared support is
  configured; whether it lands depends on the platform)
- `etc/` sample config is **not** installed by `make install`
- **No `.pc` file is installed by this recipe's configure**, so a
  `pkg-config --modversion` check does not apply — worth knowing so it is not
  reported as a missing artifact.

test -f "$OUT/include/ctags.h" || echo "MISSING ctags.h"

  test -f "$WORK/$f" || echo "GUARD INERT: $f does not exist (touch would create a stray file)"

test -f "$WORK/man/GNUmakefile" || echo "MISSING configured man/GNUmakefile"

# 3. the six flags, read back from config.log / config.h rather than assumed
grep -E 'external.sort|EXTERNAL_SORT' "$WORK/config.log" | head -3

grep -E 'checking for mblen' "$WORK/config.log"
