- Version pinned: 2.13.0

- Ships a generated `configure`: **yes** — `configure` is present and stamped

## The config template — there isn't a top-level one

This is the finding most worth stating, because three separate wrong answers
are possible here.

**hwloc has no top-level autotools config header template.** Evidence:

- `configure.ac` contains **no `AC_CONFIG_HEADERS` line at all** — grepped for
  `AC_CONFIG_HEADER` across the whole file: no matches. The only related line
  is `configure.ac:19` `AC_CONFIG_AUX_DIR(./config)`.
- There is no top-level `config.h.in`, `config.hin`, `configh.in`,
  `ac_config.h.in`, `configure.h.in`, `config-h.in` or `config_h.in`. Listing
  the top level gives only `Makefile.in`, `configure`, `configure.ac`,
  `hwloc.pc.in` and `VERSION`.

The **two `config.h.in` files that do exist** are hwloc's own hand-written
templates for its autogen headers, and they are real build inputs:

- `include/hwloc/autogen/config.h.in` — the **public** installed header,
  `nodist_include_hwloc_autogen_HEADERS = hwloc/autogen/config.h`
  (`include/Makefile.am:37`)
- `include/private/autogen/config.h.in` — the private one

Both are consumed and regenerated by `config.status` under stamp guards
(`Makefile.in:562` `include/private/autogen/stamp-h1: $(top_srcdir)/include/private/autogen/config.h.in $(top_builddir)/config.status`
and `Makefile.in:574` for stamp-h2). The recipe touches both by their real
paths so that chain stays quiet after `./configure`, exactly as it would for an
ordinary package template.

`AC_CONFIG_FILES` is likewise absent (only `configure.ac:186` `AC_OUTPUT`), so
`config.h` is not generated from a template either.

## Optional dependency probes

hwloc's `configure` is generated from its own m4 layer — `configure.ac`
contains **no `AC_ARG_ENABLE`/`AC_ARG_WITH`/`AC_ARG_DISABLE`** — so the
authoritative option list is `./configure --help`, which was read directly.
Every switch the recipe passes was verified to appear in that output and in
the generated `configure`:

`--enable-static --disable-shared --disable-picky --disable-cairo
--disable-libxml2 --disable-libudev --disable-opencl --disable-cuda
--disable-nvml --disable-rsmi --disable-levelzero --disable-gl --disable-io
--disable-pci`

All thirteen confirmed present. These are **not** API-level dependent: none of
cairo, libxml2, libudev, OpenCL, CUDA, NVML, ROCm SMI, Level Zero, GL or
libpciaccess exists in this prefix, and Bionic has no libudev at all. Each
probe is a link test, so on a cross build a probe that half-succeeds would
silently change which components get compiled per system; turning each one off
explicitly makes the component set identical everywhere.

## No target binary is ever run

hwloc builds `lstopo` and the `hwloc-*` utilities as ordinary `bin_PROGRAMS`
(`utils/lstopo/Makefile.am:19`, `utils/hwloc/Makefile.am:33-40,46,49,54`).
They are compiled as target binaries and installed; nothing in the build path
executes one. Every test and example program is a `check_PROGRAMS`
(`tests/hwloc/Makefile.am:32`, `doc/examples/Makefile.am:23`,
`tests/hwloc/embedded/Makefile.am:13`), which `make all` does not build.

The only `$(SED)` invocations in the build are post-install rewrites of
installed shell scripts (`utils/hwloc/Makefile.am:170,173`); they are upstream's
own build steps, not recipe edits.

## Per-system verdicts

The hwloc library sources were grepped for every API-level-sensitive facility
called out in this repo's notes — `nl_langinfo`, `mktime_z`, `iconv`,
`pthread_cancel`, `process_vm_readv`, `setxattr` — across `hwloc/*.c` and
`include/hwloc/*.h`. **No matches.** The only conditional code in that area is
`topology-linux.c:125-162`, a per-architecture table of raw
`__NR_sched_getaffinity` numbers, which falls back to a `sched_getaffinity`
macro returning `ENOSYS` when the architecture is unknown.

| system | verdict | reason |
|---|---|---|
| aarch64-android21 | WILL BUILD | No API-24+ facility is used. hwloc's Linux backend reaches the kernel through `sched_getaffinity`, `get_mempolicy`/`set_mempolicy`, `/sys` and `/proc` parsing and its own inline syscall wrappers — none of which is on this repo's API-21 wall list. `--disable-libudev` removes the one backend that would want a platform library Bionic lacks. The visibility feature (`--enable-visibility`, default on where supported) only adds `-fvisibility=hidden`, which clang supports at every API level. |
| aarch64-android24 | WILL BUILD | As above. |
| aarch64-android35 | WILL BUILD | As above. |
| x86_64-android35 | WILL BUILD | As above. `--disable-cpuid` is *not* passed, so the x86 component is compiled; that is plain inline CPUID asm guarded by `HWLOC_HAVE_X86_CPUID`, not a libc facility, so it is unaffected by the API level. |
| x86_64-mingw | UNCERTAIN | hwloc supports Windows (`utils/lstopo/Makefile.am:59` builds `lstopo-win` under `HWLOC_HAVE_WINDOWS`, and `contrib/windows/` ships MSVC project files), so a Windows target is in scope upstream. But **this recipe has not been tested against mingw**, and two things are worth a reviewer's attention: (1) the Windows backend wants `HwlocGetSystemTime`-style Win32 APIs and a `hwloc-dump-hwdata`/MSVC toolchain path that this cross build does not obviously satisfy; (2) `--disable-io` and `--disable-pci` are the right calls either way. I am marking this UNCERTAIN rather than guessing — the honest statement is that hwloc has a first-class Windows implementation whose configure-time probes I have not read line by line, and `HWLOC_HAVE_WINDOWS` gates several components. |
| clang-native | WILL BUILD | Native Linux/glibc. `sched_getaffinity`, `/proc` and `/sys` backends are all present. |

armv7a-androidNN and i686-androidNN behave like aarch64: hwloc's ARM and x86
components are selected by `HWLOC_HAVE_*` configure conditionals, not by the
recipe, and none of them depends on an API level.

## Risks / what a reviewer should check

- **`x86_64-mingw` is the one open question.** It is recorded as UNCERTAIN
  above rather than guessed at, and the builder should build it there before
  the recipe is considered settled for that family.
- **`--disable-io` overlaps the per-backend switches.** `--disable-io` is the
  umbrella (configure's own help says it disables "PCI, LinuxIO, CUDA, OpenCL,
  NVML, RSMI, LevelZero, GL"), so the individual `--disable-<backend>` flags
  are partly redundant. They are passed anyway so the intent survives if the
  umbrella's list changes.
- **hwloc installs a lot of target binaries** (`bin/` and `sbin/`: `lstopo`,
  `hwloc-bind`, `hwloc-info`, `hwloc-ps`, and on Linux+x86 also
  `hwloc-dump-hwdata` in `sbin`). That is hwloc's normal install shape, and
  none of them is run here.

## How to verify once built

- `lib/libhwloc.a` and `lib/libhwloc.so*` is **not** expected — `--disable-shared`
- `include/hwloc.h`, `include/hwloc/autogen/config.h` (the public autogen
  header must be installed; it is generated from
  `include/hwloc/autogen/config.h.in`)
- `pkg-config --modversion hwloc` → `2.13.0`
- `readelf -h lib/libhwloc.a` → `Machine: AArch64` on Android targets
- `grep -c . include/hwloc/autogen/config.h` must be non-zero — this is the
  file whose generation the two-template guard protects
