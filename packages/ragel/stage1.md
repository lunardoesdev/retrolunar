# ragel build forecast

- Recipe: `generic.lua`, source `source.lua` (upstream release tarball)
- Version pinned: **6.10**, not the 7.0.x series. The reason is a concrete,
  reproducible upstream defect, recorded in full under "Why 6.10 and not
  7.0.4" below. A reviewer who only reads the version field will assume
  this is a stale pin, so read that section before touching it.
- Upstream URL: `http://www.colm.net/files/ragel/ragel-6.10.tar.gz`
- Build system: **autotools** (autoconf 2.69 + automake 1.15). It also
  ships a `CMakeLists.txt`, but see "Why 6.10 and not 7.0.4" — that one is
  broken in 7.x, and in 6.10 the autotools path is the maintained one.
- A **generated `configure` ships**: 178474 bytes, and `configure:3` reads
  `# Generated by GNU Autoconf 2.69 for ragel 6.10.` (checked in the unpacked
  tree, not inferred from size).
- **Config template: `ragel/config.h.in`** — a subdirectory path, declared
  with the deprecated *singular* macro `AC_CONFIG_HEADER(ragel/config.h)` at
  `configure.ac:26`. `find . -name '*.h.in'` returns exactly one file and it
  is this one; there is no top-level `config.h.in`. This is a spelling not
  in the AGENTS.md list, which is why it is called out here.
- **Sub-configure status: not sub-configured.** There is no
  `AC_CONFIG_SUBDIRS`. The subdirectories (`ragel`, `doc`, and the
  `DIST_SUBDIRS` extras `aapl`, `contrib`, `examples`, `test`) are built by
  the single top-level configure, so one `configure` and one template is the
  whole guard. `Makefile.am:2-3` has `SUBDIRS = ragel doc` /
  `DIST_SUBDIRS = $(SUBDIRS) aapl contrib examples test` — the extras are
  distributed, not built.
- Installs: `bin/ragel` (`ragel/Makefile.am:4`, `bin_PROGRAMS = ragel` only)
  and `share/man/man1/ragel.1` (`doc/Makefile.am:21`). No library, no
  headers installed, no `.pc`.
- Requires: `ragel@source` only.

## Why 6.10 and not 7.0.4

7.0.4 is the newest tag and `releases/latest`, but **its release archive
cannot be built**. Checked directly:

1. **It ships no `configure`, no `aclocal.m4`, no `Makefile.in`.** Only
   `configure.ac`, `Makefile.am` and `autogen.sh` — it is a git checkout.
   `autogen.sh:10-17` runs `libtoolize`, `aclocal`, `autoheader`,
   `automake --foreign --add-missing`, `autoconf`, i.e. a full autotools
   bootstrap on the build host. No recipe in this tree does that.
2. **The archive is missing the `colm` directory entirely.** `configure.ac:60`
   reads `AC_ERROR([colm is required to build ragel])`; the in-tree fallback
   at `configure.ac:214` is `SUBJ_COLM_BIN='$(abs_top_builddir)/colm/colm'`.
   The 7.0.4 tarball has **zero** paths matching `colm/` (one match for
   `colm.vim`, a vim syntax file), and `Makefile.am:22` is
   `SUBDIRS = src doc test` with no `colm` to descend into. So the only way
   to satisfy it is `--with-colm=<prefix>` against an externally built colm —
   a second package, from a separate upstream, that does not exist in this
   tree.
3. **Its cmake build is structurally broken.**
   `CMakeLists.txt:61` does `add_subdirectory(colm)` and `:65` does
   `add_subdirectory(ragel)`, and **neither directory exists** in the
   archive. cmake fails at configure time.
4. **Even with colm present, the build would run a built program.**
   `src/CMakeLists.txt:103-111` generates `parse.c` with a
   `add_custom_command(... COMMAND colm:: colm -c -b rlparseC ... rlparse.lm)`.
   That is the repo's forbidden "run a target binary" case on a cross build.
5. **This is not a one-release accident.** 7.0.1, 7.0.2 and 7.0.3 each also
   contain zero `colm/` paths. The whole 7.0.x series is unusable as a
   release archive.
6. The `ragel-6.10` GitHub **tag** also has no release asset (HTTP 404), so
   the tag archive was not an option either; the colm.net tarball is the
   real 6.10 release.

ragel 6.10 by contrast is self-contained: it vendors its generated parsers
and needs no colm, no kelbt, no fig2dev.

## Native tool, not a target library

ragel compiles a state machine from a `.rl` grammar into C or C++ that is
then built into some *other* package. **The only system that actually
consumes this package is `clang-native`**, via `require("ragel@native")` —
the same shape as `packages/bison/generic.lua`'s `gperf@native` and
`packages/libnl-3/generic.lua`'s `flex@native`. `@native` resolves to
`clang-native` and falls back to this `generic.lua`, so no
`clang-native.lua` is written: it would be a byte-identical copy, the
duplicate that got `packages/bison/android.lua` deleted.

## API level notes

**No API level matters for ragel 6.10.** The `28 exposes posix_spawn` and
`35 exposes mktime_z` boundaries, and the `26 introduced nl_langinfo` one,
are all off this package's path — the grep above is empty for every symbol in
that list. So aarch64-android21 is not distinguishable from
aarch64-android35 on libc grounds, and I have not invented a reason to
separate them.

The API-gate list's other members are likewise absent: no `stderr` symbol
trick, no `O_BINARY` (unlike distcc, ragel never mentions it), no `mblen`,
no `getpass`.

## Risks / what a reviewer should check

1. **The config-template name is the trap here.** `ragel/config.h.in`, from
   the deprecated `AC_CONFIG_HEADER` singular macro — not `config.h.in`, and
   not in the AGENTS.md spelling list. `touch` on a missing file inside an
   existing directory succeeds and creates it, so a wrong name would raise
   nothing under `set -eu` and leave the autoheader re-run live. Confirmed
   present and the only `*.h.in` in the tree.
2. **The version pin is deliberate and the most likely thing to "fix".**
   Read "Why 6.10 and not 7.0.4" before bumping it. Bumping to 7.0.4 makes
   the package unbuildable, not newer.
3. **The `DIST` file is load-bearing, and `cp -r` preserves it only by
   luck of ordering.** `configure.ac:30-31` sources `$srcdir/DIST` when it is
   readable, and that is the *only* thing turning off `build_parsers` and
   `build_manual`. If `DIST` were missing, configure would default both to
   `yes` (`configure.ac:30-31`) and then `configure.ac:70-84` would hard-error
   with "ragel is required to build the parsers" / "kelbt is required". The
   recipe does nothing about this, and should not: `DIST` is an ordinary file
   in the tarball and `cp -r` copies it. Worth a glance in `stage3.md` that
   `DIST` arrived.
4. **No `touch` of the generated parser sources is needed**, and I want to
   be explicit about why, because `packages/flex/generic.lua:26-38` is the
   precedent for worrying. There, a generated `tableopts.am` shares an
   mtime with its source in the tarball and `cp -r`'s copy order decides
   whether a regeneration rule fires. Here the corresponding rule
   (`ragel/Makefile.am:55-56`, `ragel -G2 ... rlscan.rl`) is inside
   `if BUILD_PARSERS`, which is **off**, so the rule is not emitted into
   `ragel/Makefile` at all and no mtime race exists. The shipped files
   (`rlscan.cpp`, `rlparse.cpp`, `rlparse.h`) are nonetheless newer than
   their sources in the tarball — 2017-03-24 14:50:53 against 13:29:28 — so
   even if the conditional were on, they would not be stale.
5. **The man page is generated, not shipped, and that is fine.**
   `doc/ragel.1` is absent from the tarball (only `doc/ragel.1.in` is
   present) while `doc/Makefile.am:21` lists `man_MANS = ragel.1`. This
   looked for a moment like the `packages/flex` help2man trap, where
   `make install` dies on a missing page. It is not: `configure.ac:147` puts
   `doc/ragel.1` in `AC_CONFIG_FILES`, and `doc/Makefile.in:323` is the
   matching rule, so `configure` writes it. No `touch doc/ragel.1` is needed
   and adding one would be wrong.
6. **The `find . -name 'Makefile.in' | xargs touch` sweep is required, not
   decorative.** This tarball was made by automake **1.15**
   (`aclocal.m4`, `am__api_version='1.15'`), the same situation
   `packages/flex/generic.lua:33-35` documents, so the regeneration rules
   would otherwise demand a specific automake that this host does not have.
7. **`--host`/`--build` come from `$AUTOCONF_CONFIGURE_FLAGS` and nothing
   else.** No package-local flags, no exported search flags, and the
   timestamp guard is `touch aclocal.m4 configure ragel/config.h.in` plus
   the sweep.

## How to verify once built

- **`bin/ragel`** — and nothing else under `bin/`; `ragel/Makefile.am:4` has
  a single `bin_PROGRAMS`
- `share/man/man1/ragel.1`. **Its presence is the check that `configure`
  generated it from `ragel.1.in`**, and that the `DIST` file was read (a
  missing `DIST` would have aborted configure long before this)
- no `include/`, no installed library, no `.pc` — ragel's headers are
  build-time only (`RUNTIME_HDR` in the 7.x cmake, and nothing analogous is
  installed by 6.10's `install-man`)
- `file bin/ragel` → host x86_64 ELF on `clang-native`
- `bin/ragel --version` is safe to run **on `clang-native` only**
- `ls $WORK/DIST` at the end of a build proves the `build_parsers=no` input
  survived `cp -r`
