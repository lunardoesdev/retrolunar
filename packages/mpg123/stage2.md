REJECT

# mpg123 1.33.7 — review

The load-bearing claim in this package is **false**. `stage1.md` marks five
of six systems WILL NOT BUILD and the sixth UNCERTAIN, all on the strength
of a tarball fact that does not hold. Every row of that table is wrong, and
so is the recipe it produced.

## Defect 1 — the tarball is NOT ungenerated; the zero-byte claim is false

`source.lua:1-4` and `generic.lua:1-5` both assert it, and
`stage1.md:5-9` builds the entire forecast on it:

```
-- mpg123's release tarball ships ZERO-BYTE placeholders for configure,
-- aclocal.m4 and Makefile.in (verified: all three are 0 bytes in
-- mpg123-1.33.7.tar.bz2), so the tree needs a host autoreconf before
-- ./configure can run.
```

Measured in the tarball I downloaded from the recipe's own URL:

```
$ ls -l configure aclocal.m4 Makefile.in
-rw-r--r-- 458218  Makefile.in
-rw-r--r--  83526  aclocal.m4
-rwxr-xr-x 702414  configure
$ head -1 configure | tail -1
# Generated by GNU Autoconf 2.71 for mpg123 1.33.7.
```

702 KB, 83 KB, 458 KB. None is zero bytes; all three are present,
non-empty, and `configure` is a genuine GNU Autoconf 2.71 script. The
`autoreconf -fvi` at `generic.lua:19` is therefore unnecessary — and it is
not harmless, because it overwrites upstream-generated files that were
already correct. That is a rewrite of the unpacked upstream tree on the
strength of a false premise.

Consequences, all of which the adder must undo:

- `require("autoconf@native")` and `require("automake@native")`
  (`generic.lua:6-7`) are spurious dependencies. They do resolve —
  `packages/autoconf/` and `packages/automake/` both exist — so this is
  not a missing-package error; it is two unneeded packages pulled into
  every build of mpg123 on every system.
- `stage1.md`'s five "WILL NOT BUILD (needs a host autoreconf)" rows are
  void. A forecast that marks a package unbuildable on five systems for a
  reason that does not exist is exactly the "wrong forecast is worse than
  no forecast" failure AGENTS.md warns about.
- `stage1.md:66` ("Not verifiable on any cross target until the autoreconf
  question is settled") hands the builder a blocker that is not there.

## Defect 2 — `--disable-moderate` does not exist

`generic.lua:22` passes it, and `stage1.md:56-57` hedges that the option
set was never enumerated. Enumerated:

```
$ ./configure --help | grep -i moderat
(no output)
$ grep -rn "moderate" configure.ac Makefile.am
(no output)
$ ./configure --prefix=/tmp/out --disable-moderate
configure: WARNING: unrecognized options: --disable-moderate
configure: WARNING: unrecognized options: --disable-moderate
```

There is no "moderate" concept in mpg123 1.33.7's build system at all. The
flag is collected as unrecognized and ignored. Per the rule you gave me —
a nonexistent flag is worse than a missing one — this must go. (The recipe's
own comment calls it "performance tuning rather than a portability switch",
which is true as far as it goes and irrelevant: there is nothing to tune.)

## Defect 3 — the recipe bypasses the system's autoconf flags

`generic.lua:20-22`:

```lua
# mpg123's own configure, not autoconf: it does not accept
# --host/--build, and it takes its own --prefix.
./configure --prefix="$OUT" --disable-moderate
```

The premise is false — mpg123's `configure` **is** autoconf 2.71, as its
own first line says, and it accepts both:

```
$ ./configure --help | grep -E '^  --host|^  --build'
  --build=BUILD     configure for building on BUILD [guessed]
  --host=HOST       cross-compile to build programs to run on HOST [BUILD]
```

The comment is copied from the hand-written-configure family (libvpx,
ffmpeg) where it is correct, and applied to a project it does not describe.
On a cross system the result is a build with **no `--host` at all**: autoconf
guesses the host, which is exactly the failure mode the system files set
`--host=$HOST_TRIPLET` to avoid.

**Required fix:** use `$AUTOCONF_CONFIGURE_FLAGS`, which already carries
`--host=$HOST_TRIPLET --build=$BUILD_TRIPLET --prefix=$OUT`
(`packages/aarch64-android24/generic.lua:111-113`):

```lua
./configure $AUTOCONF_CONFIGURE_FLAGS
```

and delete the `--prefix="$OUT"` and `--disable-moderate`. This also fixes
question 1, which the recipe currently fails: it hardcodes the install
target instead of taking it from the system.

## What is right

- **`src/config.h.in` is the real template, and there is no top-level one.**
  Confirmed: `configure.ac:81` is `AC_CONFIG_HEADERS([src/config.h])` —
  note the **plural** spelling, unlike nettle — `find` returns
  `mp/src/config.h.in` only, and `ls -l config.h.in` is
  "No such file or directory". `generic.lua:24`'s guard
  (`touch aclocal.m4 configure src/config.h.in`) names the right file and
  sits after `./configure`, before `make`. That is correct and, given the
  `AC_CONFIG_HEADERS` plural, worth keeping written down.
- **Source URL resolves** (fetched `mpg123-1.33.7.tar.bz2`); the download
  index lists 1.33.7 as newest — **current version**. Top directory is
  `mpg123-1.33.7/`, handled by `--strip-components=1`, landing at
  `$NESTDIR/source/mpg123/`.
- `make -j1` / `make -j1 install` are fine (bare `make` is already serial;
  writing `-j1` explicitly is allowed).

## Question 1 — is it using the system?

**No**, and this is a third independent failure. The recipe reads no
build-system variable at all: no `$AUTOCONF_CONFIGURE_FLAGS`, no `$CC`,
no `$CFLAGS`. It hardcodes `--prefix="$OUT"` and passes no `--host`, so on
every cross system in this tree autoconf will guess the host triplet from
the build machine. That is the hardcoded-target-fact failure in its purest
form.

## Question 2 — the install list is largely accurate but the recipe cannot reach it

`stage1.md:10-13` names `bin/mpg123`, `bin/mpg123123`, `bin/hotplug`, the
three libraries, three `.pc` files and `man1/` pages. I did not build it —
the false premise above is disqualifying on its own and building would
compound it — so I am **not** certifying that list. Two things the adder
should verify once the recipe is fixed, since the list is currently
unexercised:

- `stage1.md:71` says "mpg123's default is libtool's, so record which
  appears" for `lib/libmpg123.a` vs `.so`. mpg123's configure decides this
  from its own defaults, and the recipe does not pass `--enable-shared` /
  `--disable-shared`; whichever it picks, a target prefix probably wants
  static. The recipe should say which, not leave it to the builder.
- `bin/hotplug` and the `out123`/`syn123` libraries ship, but nothing in
  the recipe builds a *host* copy of them, so on a cross build these are
  target binaries in `$OUT` — which is what a target prefix wants. The
  adder's note at `stage1.md:58-60` that "nothing in the recipe runs any of
  it" is correct and should be kept.

## Forecast — all six rows need re-derivation

The three Android-level rows, the x86 Android row and the mingw row are
WILL NOT BUILD for a reason that is false. The `clang-native` row is
UNCERTAIN, which is defensible in the abstract but was reached by reasoning
from a false premise too (that only the native system can host an
autoreconf). None of these rows was tested against the real tarball, and the
single fact they rested on was wrong. Rewrite the table from the tree.

## Carried to the build

Not applicable until the recipe is fixed — the current one cannot produce a
prefix to check. Once it runs, scope each check to mpg123's own artefacts:

```sh
# 1. The decoder and its raw-output helper.
[ -x bin/mpg123 ]
[ -x bin/mpg123123 ]

# 2. All three .pc files ship (all three *.pc.in are in the tree).
pkg-config --modversion mpg123            # expected 1.33.7
[ -f lib/pkgconfig/mpg123.pc ]
[ -f lib/pkgconfig/libout123.pc ]
[ -f lib/pkgconfig/libsyn123.pc ]

# 3. The .pc rewrite the loader performs: $OUT paths become $PREFIX, so
#    nothing may still name the stage dir.
grep -c "$OUT" lib/pkgconfig/mpg123.pc   # expected 0

# 4. Right machine, and a host binary would mean the cross flags never
#    reached configure.
file bin/mpg123 | grep -q 'ELF 64-bit.*x86-64' || file bin/mpg123
```

Check 3 is the one that would have caught defect 3: with `--host` missing,
the library still builds, but the prefix's search paths and the recorded
triplet in the installed metadata are the build machine's, not the target's.
Check 4's `grep -q`/`||` form is deliberate — on `clang-native` the binary
*is* x86-64, so the assertion is inverted per system rather than being a
count that fails the correct build.
