## BLAS/LAPACK — which case applies

The brief asked what Armadillo's cmake actually looks for. It has eight
optional find modules in `cmake_aux/Modules/`: `ARMA_FindARPACK.cmake`,
`ARMA_FindATLAS.cmake`, `ARMA_FindBLAS.cmake`, `ARMA_FindFlexiBLAS.cmake`,
`ARMA_FindLAPACK.cmake`, `ARMA_FindMKL.cmake`, `ARMA_FindOpenBLAS.cmake`,
`ARMA_FindSuperLU.cmake`. All are optional; none is `REQUIRED`.

**Both BLAS and LAPACK default to OFF.** `CMakeLists.txt:73-74`:

```cmake
set(ARMA_USE_LAPACK  false)
set(ARMA_USE_BLAS    false)
```

and when nothing is found, `CMakeLists.txt:485-489` prints only:

```
*** WARNING: Use of LAPACK is not enabled, as no LAPACK compatible library has been found.
*** WARNING: This will materially degrade the available functionality in Armadillo.
```

That is `message(STATUS)`, **not** a `FATAL_ERROR`. The build completes.

**Which of the two cases applies: `packages/lapack` or `packages/openblas`?**

Neither is required, and that is the deliberate answer. The reasoning:

- `packages/lapack` exists but its recipe is a **recorded blocker** — LAPACK
  3.12.1 is CMake-only with 2038 Fortran `.f` files, `CMakeLists.txt:313`
  calls `enable_language(Fortran)` with no guard, and no system in this tree
  exports `$FC`. Requiring a package that cannot build would be worse than
  requiring nothing.
- `packages/openblas` **does** build, and its recipe states plainly that
  `NOFORTRAN=1` leaves "BLAS plus the f2c-converted LAPACK, both C". So
  OpenBLAS would satisfy both roles.

Even so, requiring `openblas` would make this package's configuration depend
on the prefix's *contents* rather than on its own inputs, so the recipe
requires neither and takes Armadillo's own default. **See risk 1 — this is not
as neutral on Android as it looks.**

**Risks / what a reviewer should check.**

1. **`-DARMA_USE_LAPACK=OFF` and `-DARMA_USE_BLAS=OFF` CANNOT WORK, and the
   recipe deliberately does not pass them.** `CMakeLists.txt:72-78` introduces
   these with plain `set(...)` calls under the comment *"the settings below
   will be automatically configured by the rest of this script"*. A plain
   `set()` creates an ordinary variable that **shadows** any same-named cache
   entry created by a `-D` flag. Passing them would be silently ignored —
   which is exactly the kind of "correct-looking flag with a false
   justification" this project rejects. If a future change wants to force
   LAPACK off, it has to go through the detection switches (`option(...)` at
   `CMakeLists.txt:204` and friends), not through `-DARMA_USE_LAPACK`.
2. **The Linux detection block DOES run on our Android systems, and this is
   the one real subtlety.** `CMakeLists.txt:341` gates it on
   `if(ALLOW_FLEXIBLAS_LINUX AND (${CMAKE_SYSTEM_NAME} MATCHES "Linux"))`.
   Our cmake toolchain files deliberately set `CMAKE_SYSTEM_NAME` to `Linux`
   (AGENTS.md records this), so on **every Android system** this block fires
   and Armadillo will probe for FlexiBLAS, MKL, OpenBLAS, ATLAS, BLAS and
   LAPACK against `$PREFIX`. Right now that finds nothing, because nothing
   requires `openblas` or `lapack` and `lapack` cannot build. **But if
   `openblas` later lands in a prefix that Armadillo is built against,**
   `ARMA_FindOpenBLAS` may set `ARMA_USE_LAPACK`/`ARMA_USE_BLAS` true and grow
   `ARMA_LIBS` (`CMakeLists.txt:355-460`), which changes what the installed
   `libarmadillo.a` records as a dependency — silently, and differently on
   Android than on `clang-native`. **The builder should read the configure
   summary lines `*** ARMA_USE_LAPACK` / `*** ARMA_USE_BLAS`
   (`CMakeLists.txt:505-506`) and record them in stage3.md**, because they are
   the real evidence of which case applied.
3. **`option(HEADER_ONLY "Do not generate the wrapper library" OFF)` at
   `CMakeLists.txt:188`** means the default builds `armadillo` as a real
   library from `src/wrapper1.cpp` + `src/wrapper2.cpp` (`:580`), rather than
   as an `INTERFACE` target (`:583`). `BUILD_SHARED_LIBS=OFF` makes that a
   static archive, consistent with this prefix. Both flags are the upstream
   defaults being made explicit, not overrides.
4. **Source URL was not verifiable from the build environment.** SourceForge
   was unreachable from here (HTTP 522 and connection timeouts). The recipe
   lists the canonical SourceForge path first and falls back, on the same
   line, to the Debian pool orig tarball, which is upstream's tarball
   verbatim and is what was actually downloaded and read. Note it is a `+dfsg`
   repack; for this package that is immaterial — the tree was checked and
   still carries `examples/`, `tests1/`, `tests2/`, `docs.html`, `index.html`,
   `include/`, `src/`, `misc/` and `cmake_aux/`, so nothing the build needs was
   stripped.
5. `misc/` contains only `armadillo.pc.in` and `armadillo.spec` — Armadillo
   bundles **no** LAPACK or BLAS sources, in this tarball or (as the
   `CMakeLists.txt:31-33` comment shows, which instructs users to link
   `-lopenblas -llapack` themselves with `ARMA_DONT_USE_WRAPPER`) in general.
   Worth recording because "header library with a bundled fallback" is a
   common and incorrect assumption.
6. `topackage.md:396` lists "Armadillo"; upstream, the tarball and the
   installed artefact are all lowercase `armadillo`. The directory is named
   **`armadillo`**.

**How to verify once built.**

- `include/armadillo` exists (Armadillo's single-header entry point) — this is
  the load-bearing artifact for any consumer and proves the header install at
  `CMakeLists.txt:605` landed.
- `include/armadillo_bits/arma_version.hpp` exists and reports 15.2.1.
- `lib/libarmadillo.a` exists, proving the wrapper library was generated
  rather than skipped as INTERFACE-only.
- `lib/pkgconfig/armadillo.pc` exists and `pkg-config --modversion armadillo`
  reports **15.2.1** — this catches a stale generated version, and per
  AGENTS.md the filter `armadillo.pc` is properly scoped to this package.
- **Read the configure output for `*** ARMA_USE_LAPACK` and
  `*** ARMA_USE_BLAS`** (`CMakeLists.txt:505-506`) and record them in
  stage3.md. This is the single most informative check in this package; see
  risk 1 and 2.
- `$OBJDUMP -f lib/libarmadillo.a` prints the expected machine.
- Do not compile a throwaway consumer against it unless you are willing to
  link `-larmadillo` yourself; with LAPACK off, some Armadillo API is
  unavailable by design.
