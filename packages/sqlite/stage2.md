ACCEPT

# sqlite 3.50.4 — stage 2 review

Reviewed against AGENTS.md, the three representative systems, and the recipe.
I did not build.

## What the recipe gets right

- `--disable-shared --enable-static` is the static pair the rest of this tree
  uses, and it is unambiguous — sqlite's `configure` accepts both spellings and
  both are passed, so there is no dependence on an upstream default.
- `./configure $AUTOCONF_CONFIGURE_FLAGS` takes `--host`, `--build` and
  `--prefix=$OUT` entirely from the system, so nothing is hardcoded to a target.
- `make -j1` is explicit and serial. `make install` is an install target, not a
  compile.
- `require("sqlite@source")` names no missing package. sqlite has no library
  dependency of its own, which is why no `-D`-style path is passed.
- No `sed`, no patch, no `/dev/null`, no `export` of search flags.

## The one thing that needs checking, and it is not a defect

**sqlite's release tarball ships a pre-generated `configure` but does *not* ship
`configure.ac` or `configure.in`** — it is generated by upstream's own Tcl
toolchain from a spec kept in `autoconf/`. Two consequences:

1. `touch aclocal.m4` at line 7 touches files that **do not exist** in the
   release tarball. `touch` of a missing file in an existing directory creates
   it and exits 0 — I verified this under the emitted `set -eu`, where only a
   missing *directory* aborts — so the build continues harmlessly. But it is
   noise, and it would be *actively harmful* if it ever created an empty
   `aclocal.m4` in a tree that did have one. Worth tightening when the file is
   next edited:
   ```
        touch config.h.in
   ```

2. I could not verify sqlite's config-template name from the tree: there is no
   `nest/source/sqlite` directory in this nest, so sqlite has not been built
   here yet and I have no extracted copy to read. That is why I am not claiming
   `config.h.in` is right. **Before the build, confirm the template name** —
   sqlite's autoconf spec is at `autoconf/` in the tarball, and the generated
   `configure` itself states it near the top (`# Configuration options:` block
   names the header it generates). If it is not literally `config.h.in`, that
   line must change to match.

That is a verify-before-building item, not a known defect, so it does not make
this a reject.

## What the forecast should say about the features

sqlite's `configure` enables a great deal by default, and some of it reaches for
things this prefix does not have. `stage1.md` should state explicitly which of
these are on and whether each is safe here:

- **readline** (`--with-readline`) would want `packages/readline`, which exists.
  If sqlite's configure auto-detects it in `$PREFIX`, the linkage is correct but
  adds a dependency the recipe does not declare; if it is auto-*enabled*, it is a
  silent `require()` the recipe never wrote.
- **editline** and **tcl** must be off. tcl is in this prefix
  (`packages/tcl`), and sqlite's tclsh-based `tclsh.c` is a *host* tool that
  would be run at build time — a genuine no-emulation hazard if enabled.
- **`--enable-all` / `fts3` / `rtree` / `geopoly` / `session`**: extensions are
  fine and want no external libraries; `geopoly` optionally uses `dpkg` on Debian
  and should be off.
- **Threadsafe (`--enable-threadsafe`)**: wants pthreads, which Bionic folds into
  libc. Fine, but worth noting since `THREADS_PREFER_PTHREAD_FLAG` is an Android
  system setting that sqlite does not consult.

None of these is a recipe defect as written. The point is that `stage1.md` is
the place to record them, and if it does not, that is the forecast's gap.

## Carried to the build

- `lib/libsqlite3.a` — `llvm-objdump -f lib/libsqlite3.a | head -3` → `elf64-littleaarch64` (Android) / `pei-x86-64` (mingw). A `libsqlite3.so*` means `--disable-shared` did not take.
- `include/sqlite3.h`, `include/sqlite3ext.h` — `[ -f include/sqlite3.h ] && [ -f include/sqlite3ext.h ]`.
- `lib/pkgconfig/sqlite3.pc` — `pkg-config --modversion sqlite3` → `3.50.4`. Inside the loader's `$OUT`→`$PREFIX` rewrite set.
- `bin/sqlite3` — sqlite installs its CLI by default; `[ -x bin/sqlite3 ]` if present. It is a target program, so **never run it**.
- `bin/` — if only `sqlite3` appears and nothing else, that is the expected minimum. A `sqlite3_analyzer` or a tclsh-based tool appearing means an option was auto-enabled that should not have been; specifically, check that no tclsh-based helper was built.
- `lib/libsqlite3.la` may also appear (libtool); if so, `grep '^libdir=' lib/libsqlite3.la` must show the final prefix and not a staging path — `$OUT/lib/*.la` is inside the loader's rewrite set.
- **The check that settles the guard question:** the configure log must show sqlite generating the config header it actually uses. If a stray empty `config.h.in` appears in `$WORK` with no matching `configure.ac`, that is the harmless `touch` artefact from point 1 above — record it and move on rather than treating it as a build defect.
