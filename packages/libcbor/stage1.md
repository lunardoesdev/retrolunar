# libcbor 0.14.0 — stage 1 build forecast

- **Package:** libcbor
- **Version:** 0.14.0 (release published 2026-07-18; latest stable on the
  PJK/libcbor release list)
- **Upstream URL:** `https://github.com/PJK/libcbor/archive/refs/tags/v0.14.0.tar.gz`
  (HTTP 200, 317 101 bytes, top directory `libcbor-0.14.0/`)
- **Build system actually used: CMake** (`cmake_minimum_required(VERSION 3.5)`).
  There is no autotools anywhere in the tree — no `configure`, no
  `configure.ac`, no `Makefile.in`. The only non-cmake build file is
  `build-tests/` and `conanfile.py`, neither of which we use. **No generated
  `configure`, so the autotools timestamp guard does not apply.**

**No tools.** Upstream's `WITH_EXAMPLES` default is `ON` and builds nine
`add_executable` targets; we turn it off. It also calls
`find_package(CJSON)` (`examples/CMakeLists.txt:20`), which we do not want to
happen at all. `WITH_TESTS` is already `OFF` upstream (it needs CMocka).

`libcbor.pc` is `configure_file`'d from `src/libcbor.pc.in` and gets its
`prefix`/`libdir`/`includedir` from `join_paths` at `src/CMakeLists.txt:93-94`,
which emits `${prefix}/lib` / `${prefix}/include` rather than a baked absolute
path. The emitter still rewrites any remaining `$OUT` in staged `.pc` files to
`$PREFIX`.

The library links `m` only if `check_function_exists(ldexp)` fails
(`src/CMakeLists.txt:68-71`). See the mingw row — that probe behaves
differently on the cross systems.

## Dependencies

None. libcbor is a self-contained CBOR implementation; its only possible link
dependency is `libm` for `ldexp`, and even that is conditional. `generic.lua`
requires only `libcbor@source`.

## Per-system verdict

First, the standing caveats: **armv7a, i686 and x86_64 Android targets behave
exactly like aarch64** for this package — the library is architecture-neutral
C99 (no SIMD, no `__aarch64__`/`__arm__` anywhere in `src/`), and
`configuration.h`'s `CBOR_RESTRICT_SPECIFIER` is language, not architecture.
**The API level (21 vs 24 vs 35) is the real variable**, so I checked every
libcbor library call against API 21 explicitly: there is nothing in the set.
libcbor uses only `stdlib.h`, `string.h`, `stdio.h` and friends; no POSIX
function, no locale, no threads, no sockets, no `fork`/`exec`. There is no
API-24-or-later dependency to call out on any row.

| System | Verdict | Reason |
| --- | --- | --- |
| `aarch64-android21` | **WILL BUILD** | Three things in `CMakeLists.txt` run probes at configure time and all three are safe here. (1) `test_big_endian(BIG_ENDIAN)` (`CMakeLists.txt:16`) — modern cmake implements this from `CMAKE_C_BYTE_ORDER`, i.e. from the compiler's predefined macros, with **no `try_run`**; I read `/usr/share/cmake/Modules/TestBigEndian.cmake:82-95` to confirm. (2) `check_c_source_compiles` for `[[nodiscard]]` (`CMakeLists.txt:66-71`) and `check_c_source_compiles` for `__builtin_unreachable()` (`CMakeLists.txt:150-156`) — both are compile-only, and `-DCMAKE_TRY_COMPILE_TARGET_TYPE=STATIC_LIBRARY` (`packages/aarch64-android21/generic.lua:118`) means no link and no run. ## The one recipe flag that is doing real work: `-DCMAKE_C_STANDARD=99`

`CMakeLists.txt:66-77` probes for `[[nodiscard]]` in C. When the probe
succeeds, upstream's own comment says:

```
# Assume that if we have [[nodiscard]], we have some C23 support. May fail.
# To prevent this, pass -DCMAKE_C_STANDARD explicitly.
```

`[[nodiscard]]` is a C23 attribute. I confirmed the probe succeeds on every
toolchain we have — `clang -std=c99`, the NDK's
`aarch64-linux-android21-clang -std=c99`, and
`x86_64-w64-mingw32-gcc -std=c99` all compile a `[[nodiscard]] int f(void)`
test with exit 0. So **without our flag, all six systems would land in
`-std=c23`**, which is exactly the mode upstream flags as untested. Pinning
C99 selects upstream's other documented default (`CMakeLists.txt:86-88`, "if
(NOT DEFINED CMAKE_C_STANDARD) set(CMAKE_C_STANDARD 99)") and is the same
kind of deliberate language-level choice AGENTS.md already records for old
`bool`-typedef code.

## For a reviewer to scrutinise

1. **`CBOR_HAS_NODISCARD_ATTRIBUTE` is a PUBLIC compile definition**
   (`src/CMakeLists.txt:37-39`), so it lands in the installed
   `libcborTargets.cmake` INTERFACE properties and reaches every consumer of
   the package. Under C99 `src/cbor/common.h:87-88` then expands `CBOR_NODISCARD`
   to `[[nodiscard]]`, which is a C23 attribute being used in a C99 compile.
   Clang and gcc accept it as an extension (verified above), but a consumer
   building with `-std=c99 -pedantic-errors` would break on our `cbor` target's
   interface. Upstream created this coupling; the clean fix is upstream's.
   If a consumer ever reports it, the workaround is to build libcbor with the
   probe failing, which is *not* something to paper over in the recipe.
2. **`-DCMAKE_C_STANDARD=99` is a recipe-local language choice, not a target
   fact.** It is identical on all six systems and does not encode anything
   about a particular target, so it belongs in `generic.lua` per AGENTS.md.
   Worth a reviewer's eye precisely because it is the kind of flag that is
   usually a mistake.
3. **`WITH_EXAMPLES=OFF` is load-bearing, not cosmetic.** It is the only thing
   stopping nine target executables from being built *and* stopping
   `find_package(CJSON)` from running. Note that `packages/cjson` exists, so on
   a system where `$PREFIX` has a cJSON package the probe would have succeeded
   and two more executables would have been built.
4. **`SANITIZE=OFF`.** Upstream's default is `ON`, but it only writes
   `CMAKE_C_FLAGS_DEBUG` (`CMakeLists.txt:105-111`) and we never build `Debug`
   (the recipe does not set `CMAKE_BUILD_TYPE`). Turning it off is belt and
   braces, not a fix for an observed failure.
5. **`libcbor.pc` uses `${prefix}`-relative paths** (`src/CMakeLists.txt:93-94`
   joins `\${prefix}` with the install dirs), which is better than most of the
   other packages here. It should survive the emitter's `$OUT`→`$PREFIX`
   rewrite unchanged; if it does not, that is an emitter question, not a recipe
   one.
