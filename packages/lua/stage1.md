# lua build forecast

- Recipe: `generic.lua`, source `source.lua`
- Version pinned: 5.4.8
- Build system: **plain make, hand-driven**. Upstream ships a `Makefile` that
  assumes a Linux host, so the recipe does not invoke it; it compiles the
  objects itself and archives them. This is the one recipe in the shard that
  writes an object file by hand, and the only one that hand-writes a `.pc`.
- Installs: static `liblua.a`, the five headers `lua.h`, `luaconf.h`,
  `lualib.h`, `lauxlib.h`, `lua.hpp`, and a **hand-written**
  `lib/pkgconfig/lua.pc`. **No `lua` and no `luac` binaries** — the loop at
  `generic.lua:11-12` explicitly skips `lua.c` and `luac.c`.
- Requires: `lua@source` only. No dependencies.

| system | verdict | reason |
|---|---|---|
| aarch64-android21 | WILL BUILD | The loop compiles `src/l*.c` except the two interpreter/compiler mains, with `$CC` and `$CFLAGS` straight from the system, then `$AR rcs` + `$RANLIB`. Lua's C sources use only `malloc`, `stdio` and standard headers; `luaconf.h` is the only configuration point and it is a header, so the cross compile needs nothing else. |
| aarch64-android24 | WILL BUILD | As above; representative system. |
| aarch64-android35 | WILL BUILD | As above. |
| x86_64-android35 | WILL BUILD | As above. `$CFLAGS` is `-O2 -I$PREFIX/include` (`x86_64-mingw/generic.lua:12-15`) — no `-fPIC` on mingw, which is correct there. |
| x86_64-mingw | WILL BUILD | As above. Note the *opposite* of libffi: this recipe does **not** get `-fPIC` from the system on mingw, which is fine for a Windows static archive. |
| clang-native | WILL BUILD | As above; native `$CFLAGS` is `-O2 -fPIC`. |

**API level notes.** None. The library half of Lua is deliberately
platform-agnostic C; all the platform adaptation lives in `liolib.c`, which is
compiled but only reaches the filesystem when the interpreter runs. Since
neither `lua` nor `luac` is built, nothing here opens a file, so none of the
Android walls (`O_BINARY`, `stderr` as a symbol, `posix_spawn`) apply.
`armv7a-android*` and `i686-android*` match `aarch64-android*`.

**Risks / what a reviewer should check.**

1. **The `-DLUA_COMPAT_5_3` at `generic.lua:13` is a real behavioural
   choice**, not a workaround: it keeps the 5.3-era `lua_*` aliases
   (`lua_open`, `lua_getfield`) compiling. Any consumer written against 5.2/5.3
   API will link. Worth keeping, and worth a comment explaining it, because a
   future reader might otherwise think it is cruft.
2. **The hand-written `lua.pc` at `generic.lua:20-31` has a real bug risk that
   is worth checking carefully.** It hardcodes `Version: 5.4.8` as a literal,
   separate from the `version = "5.4.8"` in `source.lua`. **When lua is
   updated, only one of the two will be updated** and the `.pc` will report the
   old version. That is a genuine maintenance trap. `libffi`, `libogg` and
   every other package in this shard get their `.pc` version generated by the
   build system, so this recipe is the odd one out.
3. **`Libs: -L${libdir} -llua -lm`** hardcodes `-lm`. On glibc that is
   redundant but harmless; on the Android systems it is *load-bearing*, because
   Bionic keeps the math functions in `libm` and Lua calls `pow`/`log` — which
   is exactly what `aarch64-android24/generic.lua:79` documents. So the two
   `-lm`s are redundant with each other on Android and belt-and-braces is
   fine. On mingw, however, `-lm` is **wrong**: there is no `libm` in a PE
   toolchain. If this recipe has ever been built on `x86_64-mingw`, either
   mingw tolerates a missing `-lm` or the recipe has not been run there.
   **This is the most likely real defect in this file.** What would settle it:
   build lua on `x86_64-mingw` and look for a `cannot find -lm` link error, or
   check with a throwaway consumer that `pkg-config --libs lua` resolves there.
4. **`topackage.md` has no entry for lua**, and nothing else in the tree
   `require()`s it. So it is a standalone with no recorded build — same gap as
   libwebp, libvpx and the pure-Python packages.
5. **Skipping `lua.c` and `luac.c` is right, but note the `case` pattern at
   `:11-12` matches on the full path** (`*/lua.c|*/luac.c`). That is correct
   for the `src/` layout and would break if the sources moved. Fine today.
6. The `for _s in src/l*.c` glob means any future `src/lSomething.c` is picked
   up automatically. That is the desired behaviour, and it is why `lmatrix.c`
   and friends work without listing them.

**How to verify once built.**

- `lib/liblua.a` exists; `include/lua.h`, `luaconf.h`, `lualib.h`,
  `lauxlib.h` and `lua.hpp` all exist.
- `lib/pkgconfig/lua.pc` exists and `pkg-config --modversion lua` reports
  **5.4.8** — this is the check that catches trap 2 above.
- `$OBJDUMP -f lib/liblua.a` prints `elf64-littleaarch64` on Android.
- `llvm-nm --defined-only lib/liblua.a | grep -cw lua_gettop` non-zero, and
  `grep -cw lua_open` also non-zero — the latter proves `LUA_COMPAT_5_3` took.
- `llvm-nm --undefined-only lib/liblua.a | grep -cw 'pow\|log'` — should be
  non-zero, which is what makes the `-lm` in the `.pc` correct on Android.
- On `x86_64-mingw` specifically, watch for a `cannot find -lm` link error —
  see risk 3 above.
