# libxcrypt build forecast

- Recipe: `generic.lua`, source `source.lua`
- Version pinned: 4.5.2, from the **besser82/libxcrypt fork** (upstream
  `bminor/libxcrypt` 404s for every release tarball, per `topackage.md:51`).
- Build system: autotools
- Installs: `libcrypt.a`/`libcrypt.so`, `crypt.h`, `libcrypt.la`,
  `libxcrypt.pc`, and the `xcrypt` binaries. The two `.pc`/`.la` names differ
  by build type, so expect the static one.
- Requires: `perl@native` (exists) — for the configure-time helper scripts.

| system | verdict | reason |
|---|---|---|
| aarch64-android21 | **WILL NOT BUILD** | Not the recorded blocker — see below. The wall is a link-time version-script failure. |
| aarch64-android24 | **WILL NOT BUILD** | Same. |
| aarch64-android35 | **WILL NOT BUILD** | Same. |
| x86_64-android35 | **WILL NOT BUILD** | Same. |
| x86_64-mingw | **WILL NOT BUILD** | Same: the version script is applied by the linker regardless of target, and the symbol set it names is the same. |
| clang-native | **WILL NOT BUILD** | Same. The failure is in libxcrypt's own version-script generation, not in Bionic, so glibc hosts fail identically. |

**The recorded blocker, faithfully.** `topackage.md:51` describes **two**
stages and is explicit that the first is already solved:

1. **SOLVED** — the original failure was the native perl's unusable `@INC`,
   now fixed (see the perl 5.44.0 entry). The recipe still carries that fix at
   `generic.lua:9`: `export PERL5LIB="$NATIVE_PREFIX/lib/perl5/5.44/core_perl"`.
   So configure and its perl helpers run cleanly.
2. **REMAINING** — linking `libcrypt.la` fails with
   `ld.lld: error: version script assignment of 'XCRYPT_2.0' to symbol
   'xcrypt' failed: symbol not defined`, and likewise for `crypt_gensalt_r`,
   `xcrypt_gensalt` and `xcrypt_gensalt_r`. The version script is generated by
   `build-aux/scripts/gen-libcrypt-map` from `lib/libcrypt.map.in`, which lists
   those five symbols only when a compatibility ABI is selected — and
   4.5.2's does not select one.

**API level notes.** None. **No Android API level fixes this.** The blocker
is a version-script/symbol-set mismatch inside libxcrypt's own build, present
on every target including glibc. Anyone reading the `android21` row and
thinking "try android35" would be wasting time.

**Risks / what a reviewer should check.**

1. **The `--enable-hashes=strong,glibc --enable-obsolete-api=glibc` at
   `generic.lua:11-12` is the most likely culprit and the recipe does not say
   so.** These two flags are what select the `glibc` compatibility ABI — and
   per `topackage.md:51` the version script lists `xcrypt`,
   `crypt_gensalt_r`, `xcrypt_gensalt` and `xcrypt_gensalt_r` *only when a
   compatibility ABI is selected*. So the recipe appears to be asking for
   exactly the ABI whose symbols then fail to link. **A reviewer should try
   this package without those two flags** before concluding it is blocked.
   That is a concrete, cheap experiment and the forecast's main actionable
   suggestion.
2. **The `PERL5LIB` workaround is still there and still needed**, correctly
   commented and using `$NATIVE_PREFIX` with nothing hardcoded. Same pattern
   as `intltool`. This is stage 1 of the two recorded stages and it is holding.
3. **`make` at `:16` is not `make -j1`** — the usual rule deviation.
4. **libxcrypt is a libc-adjacent library**, so a reviewer should think about
   whether it belongs in an Android prefix at all. Bionic has its own
   `libcrypt` (tiny, DES/MD5 only), and a second `crypt()` in the prefix is a
   link-order hazard for any consumer. This is a design question, not a build
   question, but it belongs in the record.
5. `topackage.md:51` is accurate and unusually precise — it names the exact
   linker diagnostic, the exact generating script, the exact `.map.in`, and
   which five symbols are involved. **This is the model for how a blocker
   entry should be written.**

**How to verify once unblocked.**

- `lib/libcrypt.a` exists; `include/crypt.h` exists.
- `pkg-config --modversion libcrypt` (or `libxcrypt`) reports 4.5.2.
- `llvm-nm --defined-only lib/libcrypt.a | grep -cw xcrypt` must be
  **non-zero**. Zero is the exact signature of the recorded failure — the
  version script demanded `XCRYPT_2.0:xcrypt` and the archive does not define
  it.
- Check the generated map before linking: `grep -c 'xcrypt' lib/libcrypt.map`
  in the build tree. If the five symbols are absent, the ABI flags are the
  problem.
- The build log must contain no `version script assignment ... failed`. That
  string is the whole blocker in one line.
