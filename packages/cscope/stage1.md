# stage1 — cscope 15.9 (build forecast)

## Native or target?

**Target.** cscope is an ordinary program — an interactive C-source
browser. It does not invoke or intercept a compiler, does not
`LD_PRELOAD` anything, and needs nothing from the build host at run time.
It links against curses and uses `lex`/`yacc` **as build-time code
generators**, which is the ordinary target-package shape, not the
compiler-adapter shape. So this package has a normal `generic.lua` and no
`clang-native.lua`.

## flex and bison must run, so they are native

`src/Makefile.am:25` lists `$(LEXER_SOURCE)` and `egrep.y` in
`cscope_SOURCES`, so automake regenerates the scanner and the parser during
the build, and `src/Makefile.am:22` sets `BUILT_SOURCES=egrep.h`.
Those generators **execute** on the build host, so a target build cannot
use them. They are therefore `require("flex@native")` and
`require("bison@native")`.

This matters for API 21 specifically: bison and flex are host binaries and
are unaffected by the Android API level.

Which lexer is used depends on `$LEX` (`configure.in:16-20`): if `LEX` is
literally `lex`, `scanner.l` is used; otherwise `fscanner.l` and the flex
path. Both `.l` files ship, and the pre-generated `src/fscanner.c`
(1800055 bytes) and `src/egrep.c` (60873 bytes) ship as well — but
`src/Makefile.am:40` lists `scanner.c fscanner.c egrep.c` in `CLEANFILES`,
and the regeneration rules can still fire, so flex and bison are genuinely
required rather than merely belt-and-braces.

## The curses situation — read before trusting the "WILL BUILD" rows

`configure.in:254-265` (`AC_SEARCH_NCURSES`) searches a **hardcoded list of
host paths only**: `/usr/include`, `/usr/include/ncurses`,
`/usr/local/include`, `/usr/local/include/ncurses`. It never consults
`$PREFIX`. The repo has a `packages/ncurses`, but this recipe does not
`require` it, because `--with-ncurses=DIR` (configure.in:154-166) hardcodes
`-L$DIR/lib -lncurses` and `-I$DIR/include` and bypasses the search — and
pointing a cross build at the wrong ncurses is worse than not having one.

Consequence, stated plainly: **whether cscope gets a working curses
implementation on a given system is UNCERTAIN**, and it degrades rather
than fails. With `has_curses=false`, `src/Makefile.am:35`
(`cscope_LDADD = $(CURSES_LIBS) $(LEXLIB) $(LIBOBJS)`) links with empty
`CURSES_LIBS`. Whether the result is a useful viewer or a broken one is not
something this forecast can settle without building.

`--with-regex` is not passed; `configure.in:357` does
`AC_CHECK_LIB(regex, regcomp)`, which is fine on all six systems.

## Note on the upstream URL

`source.lua` fetches from the Debian pool because
`github.com/dscscope/cscope` is blocked by this environment's egress
proxy: `github.com/dscscope/cscope`, its `/releases` and `/tags` pages,
`codeload.github.com/dscscope/cscope/...`, and
`raw.githubusercontent.com/dscscope/cscope/master/README.md` all return
404, repeatedly and with `--retry`. The same 404 comes back for
`github.com/bminor/bash`, a repository that certainly exists, so **this is
a proxy filter and not evidence that the repository is gone**. I am
recording it rather than "fixing" it: if the proxy is lifted, the recipe
should switch to the upstream release tarball, and the version should be
re-checked against the real latest release.

## Notes for the reviewer

- Guard is `touch aclocal.m4 configure config.h.in`, then
  `find . -name 'Makefile.in' | xargs touch`. `config.h.in` is the real
  name; `touch` on a wrong name inside an existing directory would succeed
  silently and leave the autoheader re-run live.
- No ncurses flag is hardcoded, and no search flag is `export`ed.
- Build never fans out: `make -j1`.
