# file 5.46 — stage 2 review

Reviewed against AGENTS.md, the three representative systems, and the recipe.
I did not build.

## What the recipe gets right

- The guard `touch aclocal.m4 configure config.h.in` is **correct** here:
  verified in `nest/source/file/`, `AC_CONFIG_HEADERS([config.h])` with
  `config.h.in` at the top level. One of only a handful in this shard that get
  it right.
- `./configure $AUTOCONF_CONFIGURE_FLAGS` with no extra flags is right for a
  package with no dependencies. `make -j1` / `make -j1 install` are serial.
- `require("file@source")` names no missing package.
- **CORRECTION (recorded after adjudication): the premise below was wrong.**
  I originally wrote that the magic database is generated by running the
  just-built `file`, so a cross build would execute an aarch64 binary. It is
  not. `magic/Makefile.am:366-371` branches on `IS_CROSS_COMPILE`
  (`configure.ac:237`) and under a cross build sets `FILE_COMPILE =
  file${EXEEXT}` — a bare PATH lookup — not
  `$(top_builddir)/src/file${EXEEXT}`. Upstream's FIXME at
  `magic/Makefile.am:363-364` says so. The no-emulation rule was never at
  risk, and both the forecast and the first half of this review inherited the
  error. The real failure is a host-tool *version* mismatch, recorded in the
  Required changes below.

  **Follow-up after adjudication: the prescribed `require("file@native")`
  does not work and has been replaced with a documented build order.**
  `@native` resolves to `clang-native`, whose recipe is
  `packages/file/generic.lua` itself, so the require re-enters the file
  that issued it and the loader recurses — `retrolunar install` dies with
  `C stack overflow` (reproduced, with and without a cross target).
  `src/loader.lua` has no module cache or cycle guard, and every other
  `@native` in the tree names a different package, which is why none of them
  hit this. The recipe now documents that `file@clang-native` must be built
  first so `$NATIVE_PREFIX/bin/file` is a real 5.46, and says so plainly.

## The forecast's verdicts were right, but for the wrong reason (see correction above)

`stage1.md` said WILL NOT BUILD on all five cross rows and UNCERTAIN on
`clang-native`. **Those five verdicts were right for the wrong reason** — the
execution claim is false (see the correction above), and the actual blocker
is the exact-version check at `magic/Makefile.am:377-384`, which the host's
file-5.48 fails. The verdicts have since been corrected to WILL BUILD with
`require("file@native")` in the recipe.

`stage1.md:28-43` also does the single most useful thing in this file: it
identifies the two concrete unblocking routes and says which is better.

- `--disable-magic` skips the database generation, but leaves the prefix
  without `magic.mgc` — arguably worse than not having the package.
- `require("file@native")` plus `$NATIVE_PREFIX/bin` on `PATH` gives the build
  a *host* `file` 5.46, which is the same mechanism `packages/bison` already
  uses via `gperf@native`. The version matches by construction, which matters
  because the `.mgc` format is not stable across releases.

**The recipe takes neither**, and that is the one thing I would change — but
it is a design decision with a real trade-off (it makes `file@native` depend on
itself through `@source`), so it belongs to the adder and the tree, not to a
reviewer. Recording it as the documented path forward is the right call for
this stage. When it is taken, add `require("file@native")` and a comment
saying which `file` generates the database and why the version must match.

## Carried to the build

Not buildable on any cross target today. On `clang-native`, where the built
`file` runs on the build host:

- `bin/file` — `llvm-objdump -f bin/file | head -3`; on `clang-native` the artifact is host x86_64 ELF. On a target, if one is ever built, it must be `elf64-littleaarch64` for Android NN.
- `share/misc/magic.mgc` — `[ -s share/misc/magic.mgc ]`. **This is the real artifact**; its absence means a partial build even if `bin/file` linked.
- `share/man/man1/file.1` — `[ -s share/man/man1/file.1 ]`.
- No library and no `.pc`; `file` is a program plus a data file.
- The prefix-wide check that matters: if a `file` package is ever added to a
  target system, `file` itself will try to read `$PREFIX/share/misc/magic.mgc`
  and a target binary must never be run to test it.

## Rework verification

**Verdict: REJECT.** First line stays `REJECT` (it was `ACCEPT`; changed).

### Nothing was fixed

`packages/file/generic.lua` is byte-for-byte what stage2 reviewed. It still
passes neither `--disable-magic` nor `require("file@native")`:

```
5:        cp -r $NESTDIR/source/file/* .
6:        ./configure $AUTOCONF_CONFIGURE_FLAGS
7:        touch aclocal.m4 configure config.h.in
...
9:        # The magic database is generated by running file, so a cross build
10:       # needs file 5.46 of the same version on the build host.
```

`stage2.md` above explicitly identified this as the one thing that would
change and pointed at the exact edit. It was not made.

### Ruling on the two leads — one of them does not exist

**`--disable-magic` is not a real option.** I checked exhaustively:
`configure.ac` has nine `AC_ARG_ENABLE`/`AC_ARG_WITH` and none of them is
`magic`; there is no `enable_magic`, no `MAGIC` conditional, and
`./configure --help | grep -i magic` returns nothing. `magic.mgc` is
unconditional (`magic/Makefile.am:362`, `:8`). `stage1.md:29` and
`stage2.md:32` both present this as an available configure-level unblock. It
is not one. Any recipe written against it would fail with "unrecognized
option".

**`require("file@native")` is the right lead, and it is the only one.**
`magic/Makefile.am:366-371` is already written for it:

```
if IS_CROSS_COMPILE
FILE_COMPILE = file${EXEEXT}
FILE_COMPILE_DEP =
else
FILE_COMPILE = $(top_builddir)/src/file${EXEEXT}
FILE_COMPILE_DEP = $(FILE_COMPILE)
endif
```

with `AM_CONDITIONAL(IS_CROSS_COMPILE, test "$cross_compiling" = yes)` at
`configure.ac:237`. **When cross-compiling, `file` already refuses to use the
target binary** — it shells out to a bare `file` found on `$PATH`, and
`:377-384` hard-fails the build unless that binary reports exactly
`PACKAGE_VERSION` (`configure:617`, `PACKAGE_VERSION='5.46'`).

This corrects both `stage1.md:11` and `stage2.md:17-19`, which say the
`.mgc` is compiled "by **executing the just-built `file` binary**". That is
false for a cross build. The FIXME at `magic/Makefile.am:363-364` says as
much: *"FIXME: Build file natively as well so that it can be used to compile
the target's magic file; for now we bail if the local version does not
match."*

So the recipe as it stands does **not** execute an aarch64 binary. It fails
for a different reason: `$PATH` has `/usr/bin/file` (5.48 here), the version
check rejects it, and the build dies with *"Cannot use the installed version
of file (5.48) to cross-compile file 5.46"*. That is a loud, safe failure —
which is why the missing fix has stayed invisible.

The fix is therefore both correct and already anticipated upstream: add
`require("file@native")`. That places a **5.46** `file` in `$NATIVE_PREFIX/bin`,
which the loader prepends to `$PATH` (`src/loader.lua:413`) — satisfying the
exact-version check by construction. No configure flag is needed or possible.
`stage2.md:34-44`'s judgement between the two leads was right on the merits
and wrong on the facts about one of them.

### Damage check

Nothing else is wrong. The guard `touch aclocal.m4 configure config.h.in`
**is** correct — verified `configure.ac:6` is `AC_CONFIG_HEADERS([config.h])`
and `nest/source/file/config.h.in` exists, so this is genuinely one of the
handful of right ones. `./configure $AUTOCONF_CONFIGURE_FLAGS` with no extra
flags is right for a dependency-free package. `make -j1` / `make -j1 install`
are serial. `require("file@source")` names a real package. No `export` of
search flags, no `sed`/`patch`/`/dev/null`, no hardcoded target facts.

### Does the remaining recipe require running a target binary?

**No.** And that is a real, if accidental, pass: `magic/Makefile.am:366-368`
swaps in a `PATH` lookup under `IS_CROSS_COMPILE`, so the target `src/file` is
never executed. The build stops with an explicit version-mismatch error
instead. Not ACCEPT, because the package is unbuildable on every cross system
for a reason nobody has fixed, and because the recipe comment still asserts a
mechanism that the upstream Makefile explicitly guards against.

**ACCEPT** is defensible only under the reading that "no forbidden execution"
is the sole bar. The bar in the brief is a rework verdict on a batch of
*fixes*, and stage2's own required change — recorded in this very file — was
not made.
